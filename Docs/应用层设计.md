# 应用层设计（以源码为准）

> 本文描述 `AutomatedLine.Application` 层四个核心后台组件与天车状态机，内容**按当前源码实际实现**整理：
> `DeviceStateCollector`、`TransportTaskGenerator`、`CraneScheduler`、`CraneWorker` 与状态机。
> 另含状态机**全部流程的逐步说明**（读了哪些信号、下发了哪些参数）。
> 寄存器/宏变量点位见《设备寄存器地址/》，程序参数见 appsettings 的 `App` 节点。

---

## 1. 总览：一条工件如何被搬运

```
DeviceStateCollector（设备采集，常开）
        │  写 device.Signals（输入信号快照）
        ▼
TransportTaskGenerator（候选生成，线路运行中）
        │  产出 CandidateTaskPool（全枚举）
        ▼
CraneScheduler（集中调度，只判断）
        │  TryTransition(Waiting→Assigned) 后 Writer.TryWrite 入队
        ▼
CraneTaskChannels（每车一个容量 1 队列）
        ▼
CraneWorker（每车一个独立循环，独占写 Crane.Runtime）
        │  RunFlowAsync → 6 个设备 handler + 通用原语
        ▼
设备/天车 PLC（Modbus / FOCAS）
```

| 组件 | 周期（配置项，默认） | 源码 |
|---|---|---|
| `DeviceStateCollector` | `Collection.DeviceIntervalMs`（500ms） | `Application/Collection/DeviceStateCollector.cs` |
| `TransportTaskGenerator` | `Scheduling.GenerateIntervalMs`（500ms） | `Application/Generation/TransportTaskGenerator.cs` |
| `CraneScheduler` | `Scheduling.ScheduleIntervalMs`（500ms） | `Application/Scheduling/CraneScheduler.cs` |
| `CraneWorker` | `StateMachine.ExecuteIntervalMs`（500ms） | `Application/Workers/CraneWorker.cs` + `CraneStateMachine.cs` |
| `RuntimeTaskManager` | 无周期（UI 触发增删/启停） | `Application/Runtime/RuntimeTaskManager.cs` |
| `TaskAbortCoordinator` | 无周期（异常触发） | `Application/Alarms/TaskAbortCoordinator.cs` |

> **共享状态（都在内存，进程内唯一）**：`RuntimeTaskManager`（工件任务总表）由 UI 添加/启动/暂停，被生成器、调度器、状态机读写；
> `DeviceRegistry` / `CraneRegistry` / `DriverRegistry` / `CandidateTaskPool` / `CraneTaskChannels` /
> `RightOfWayManager` / `ResourceReservationManager` 都是**启动时装载、运行期只在内存**的对象目录。
> 全场只有一次 DB 访问在运行期：状态机取设备坐标（`BaseOfAsync` → `IConfigurationStore`，每任务一次）。
>
> **异常路径**：状态机 `catch` → `TaskAbortCoordinator.Abort` → `AlarmManager.Raise`（写 `alarm.txt` + 事件）→ UI（`App`）弹窗。

## 2. DeviceStateCollector（设备采集）

**职责**：周期性并发读取**所有已装载设备**的输入信号，整体替换 `device.Signals`。**只采设备，不采天车**（天车按需读）。

- 周期 `Collection.DeviceIntervalMs`；单次请求超时 `Collection.CommunicationTimeoutMs`（注入 Modbus 客户端）。
- **并发**：每台一个 `Task`（`drivers.Select(d => ReadOneAsync(d, sequence, ct)).ToList()`）后 `Task.WhenAll`，
  **全部完成后**才统一替换缓存（`ToList()` 不可省——否则 `IEnumerable` 会被重复枚举、重复启动任务）。
- **轮次序号**：每轮 `Interlocked.Increment(ref _sequence)` 作为快照版本号写进 `Snapshot.Sequence`（便于判断新旧）；轮次结束记 `LastCollectedAt`。无驱动时只更新 `LastCollectedAt` 直接返回。
- **只读输入信号**：**Modbus 设备**按点位表只读 `Writable=false` 的点（请求/完成/状态等），下发参数与握手输出只写不读；
  **斜床（FOCAS）**没有"可写位"概念，固定读一张宏变量列表（`#1001~#1005` + `#1101~#1105`）。
- **失败处理**：单台失败/超时 → 写一份"断开空快照"（`ConnectionState.Disconnected`、`Quality=Bad`、`Values` 为**空字典**），**不重连、不报警**（报警只来自状态机异常/系统）。底层 `ModbusTcpClient` 下次调用会自动重连。
  - **替换只对"注册表里查得到的设备对象"生效**：`DeviceRegistry.Get(driver.DeviceId)` 未命中时**保留旧快照**（不会清空）。
  - ⚠️ 失败时 `Signals` 是**空快照而不是 `null`**，所以"有没有数据"只能看 `IsConnected`（= 快照里的 `ConnectionState`），**不能**用 `Signals is not null` 判断。
- **日志**（都在 `collection.txt`）：成功后按抽样写一条采集心跳（键 `collection-device`，默认 20s 一条）；单台失败按设备号抽样（键 `collection-fail-<id>`），详见 §11。
- 采集与线路启停**无关**：无论线路是否运行，设备信号一直读（保证候选生成时数据是新的）。

> 天车**不做后台采集**：调度选车、状态机预检、冷启动核对、大屏刷新都**按需**调用 `ICraneDriver.ReadStatusAsync`，避免与运动轮询争抢 Modbus 连接。
> 这是**结构保证**：采集器只取 `DriverRegistry.Snapshot().OfType<IDeviceDriver>()`，而 `ICraneDriver` **不继承** `IDeviceDriver`（两者在 `DriverRegistry` 里是两张独立表）。
> 另：**没有真实驱动的设备类型**（货叉/动平衡/验点等）不会进驱动表 → **永远没有信号快照**，`CanProvide/CanReceive` 一律 false（等于该工序不参与）。

## 3. TransportTaskGenerator（候选任务生成）

**职责**：每周期根据当前内存与设备信号**整体重建**候选池（Snapshot/Rebuild，不是队列）。

**门控**：
- 线路级：仅 `LineControlService.IsRunning` 时生成；否则**在候选池非空时**才 `Clear()`（空清空会白白触发界面刷新），并写一条 `generate-idle` 抽样日志。
- 任务级：只处理 `WorkpieceState.Waiting`（已启动入线）的工件；未启动（`Created`）/暂停（`Paused`）/已派发等跳过。

**算法（`GenerateOnce`）**：
1. 取入线任务 `lineTasks = Snapshot().Where(TaskState==Waiting)`。
2. **队头** = 在队列（`CurrentLocation.Kind==Queue`）且 `QueueOrder` 最小者（上料架取板顺序）。
3. 对每个入线任务：
   - 解析**源**（`ResolveSource`）：在设备上 → 该设备（要求内存一致 + 已连接 + 未预约 + 未报警 + `CanProvide`）；在队列 → **仅队头**，源=唯一上料架（要求 `IsEnabled + IsConnected + 未预约 + 未报警`，最后看 `HasMaterial`）；两者都不满足时以 `工件位置异常（…）` 兜底返回 null。
   - 下一道工序 `ProcessRoute.GetNextAvailable(current, ProcessRoute.AvailableDeviceFilter(devices))`：判据只有一个 ——「该设备类型有没有启用设备」。**无设备的工序自动跳过；有设备的工序必经**（设备离线/报警时工件停下来等它，不绕过去）；返回 null → 工件置 `Completed`。
   - **目标全枚举**：同类型设备中满足 `<IsEnabled、≠源、IsConnected、未预约、未报警、CanProcess(直径,长度)、CanReceive>` 者**每个生成一个候选**（`Priority` 暂固定 100）。
4. `_candidatePool.Replace(candidates)`。

**就绪判定 `DeviceHandshakeRules`**（读输入信号快照，无快照视为不就绪）：
- `CanProvide`：上料架 `HasMaterial`；双头镗/斜床/研磨 `RequestUnload`；打号 `ProcessDone`。
- `CanReceive`：双头镗/斜床/研磨 `RequestData`；打号机 `Busy==false`（0001 的 **0=空闲**）；下料架 `HasMaterial==false`。
  后两者**都要求有采集数据**（`Signals is not null`）——无快照视为"未知"，不能当成"空闲可放"。
- `IsAlarm`：目前**只有研磨机**有点位（`RunState==2` 机床报警），其余设备恒为 false。

## 4. CraneScheduler（集中式调度）

**职责**：全系统**唯一**调度器，决定"哪个候选任务 → 哪台天车"。**只做只读判断，不写 `Crane.Runtime`**。

**每轮（`DispatchOnceAsync`）**：
1. **整轮受 `LineControlService.IsRunning` 门控**（线路未运行时根本不派发）。候选池为空 → 本轮直接返回，并登记"候选池为空"
   （`ReasonChangeLog`：**变化时才落盘**；恢复时写一条 `调度 已恢复（上一轮原因：候选池为空）`，见 §11）。
2. 对"启用且空闲"的天车**逐台顺序**读一次状态（`ReadIdleCraneStatusesAsync` 内 `foreach` + `await`），存本轮字典；
   每次读 ≈ 2 次批量寄存器（`D5000~D5029` + 速度区）+ 最多 9 次 X 区线圈 ≈ **11 次 Modbus 往返**；读失败该车记为 `null`（本轮排除）。
   ⚠️ 因为是**顺序**读：某台天车离线时，本轮要等它的通信超时（`Collection.CommunicationTimeoutMs`，默认 3s）才能继续 → 派发被拖慢（已知待改进点）。
3. 候选排序：**优先级降序 → 最近可执行天车到源的距离**（不做负载均衡）。
4. 逐个候选：
   - 跳过非 `Waiting` 的。
   - 算**可执行天车** `eligible`：`IsEnabled && IsIdle && Covers(源X) && Covers(目标X) && 状态可读 && !HasAlarm`，按**离源最近**排序。
     路权区间按**每台车各自的宽度**现算（`GetRightOfWayInterval(crane.Width)`）；状态读不到的车记 `null`、只记一条 `Communication` Warn 后排除。
   - 逐台天车尝试（换车）：`CanAcquire(任务区间)`（只读）、`IsReserved(源/目标)`（只读）；通过后：
     - **原子占位**：`task.Runtime.TryTransition(Waiting, Assigned)`（`Interlocked` CAS，只成功一次）。
     - **入队**：`channel[crane.Id].Writer.TryWrite(transportTask)`；失败（队列已满）→ 回退 `Assigned→Waiting`，换下一台车。
     - 成功即**只入队**，**不碰 `Crane.Runtime`**（天车状态由该车 Worker 独占）。

**判据细节**：`CanAcquire` = 路权区间不与任何在途任务区间相交；`IsReserved` = 设备已被别的任务预约。真正的 `TryAcquire`/`TryReserve` 在状态机执行时完成（拿不到则回滚）。

**日志**：候选池为空、逐候选"天车筛选原因"、路权/预约冲突都走 `ReasonChangeLog`（**变化时落盘 + 恢复行**，见 §11）；
其中"天车筛选原因"仅在**本轮确有天车被排除**时（`eligible.Count < 天车数`）才登记。

## 5. CraneWorker 与状态机

### 5.1 CraneWorker（每车一个独立循环）
- 启动时对**每台启用天车**起一个 `Task.Run` 循环。
- 循环体：线路运行中且 `channel[crane.Id].Reader.TryRead(out task)` → 设置 `Crane.Runtime.CurrentTask/State`（**本循环独占写本车 Runtime**）→ `await StateMachine.RunFlowAsync(...)`；异常兜底清 Runtime。
- 一台车一次只跑一个任务（"一车一任务"由 `Crane.IsIdle` 判定 + 队列容量 1 **双保险**）；多车真正并行。
  注意槽位在 Worker `TryRead` 那一刻就空了——容量 1 只保证"同时最多一条待执行"。
- 每轮末尾 `await Task.Delay(Max(50, StateMachine.ExecuteIntervalMs))`；该周期**只在循环启动时读一次**（改配置要重启才生效）。
- 取消（`StopAsync` / 宿主关闭）时：`FallbackAbort` + `ClearRuntime` 后 **`throw;`** → 该车循环**永久退出**，且该 `Task` 从未被 `await`（`_loops` 只 `WhenAny`）→ 异常无人观察；正常关机场景无影响。

### 5.2 任务交接：CraneTaskChannels
- 每车一个 `Channel<TransportTask>`（容量 1、单读者）。调度器只 `TryWrite`；Worker 只 `TryRead`。从根上消除"两线程写同一 `Crane.Runtime`"的竞态。
  注意 `Crane.Runtime.State=Reserved` 由 Worker 出队后才置（**派发不写 Runtime**），所以同一轮里同一台车可能再次入选——
  由容量 1 的 `TryWrite` 失败回退换车兜住（会白付一次 CAS + 回滚）。

### 5.3 编排器 RunFlowAsync
```
Acquire             原子 TryAcquire 路权 + TryReserve 源/目标；失败→回滚、任务回 Waiting
AuditSource         再审核源（内存一致；源 PLC 信号由 handler 首步等待）
SetSpeed            ctx.SetCraneSpeedAsync：下发本车 X/Y/Z 速度/加速度/减速度
PickAsync(源类型)   取料（见 §6）
TransitAsync       XY→目标上方；释放源预约；路权缩小到 [target±w/2]；**复位源与目标两侧握手位（先源后目标）**
PlaceAsync(目标类型) 放料（见 §6）
FinishAsync        X 回安全位；释放路权 + 目标预约；置 TaskState
```
- 状态：`AcquireResources` 成功后 `Crane.State=Running`、`wp.TaskState=Running`。
- **每一步之前都会设置 `phase`**（如 `审核源(双头镗)`、`取料(斜床1)`、`中转(斜床1→研磨机)`、`放料(研磨机)`、`收尾`），
  异常日志与弹窗用它标出**卡在哪一步**（见 §11、§12）。
- 任务开始/完成各写一条 `StateMachine` 日志，内容含**工件版号/序号 + 源→目标**（见 §11 命名约定）。
- **异常统一处理**（不区分充磁前后，见 §7）：状态机流程内任何异常 → `TaskAbortCoordinator.Abort`：
  **释放天车状态 + 释放路权 + 释放源/目标设备预约 + 清理当前任务 + 暂停线路 + 写日志 + 弹窗**。
  重启线路后，只要 PLC 信号正确，天车照常继续工作。
- `HasPieceOnCrane` 仅用于**异常信息提示**（板是否可能在天车上），**不再**决定处理分支。

### 5.4 TransferContext（流程原语）
每个任务构造一个，提供：
- `BaseOfAsync(device)`：设备库 X/Y/Z **现查**（`IConfigurationStore`，本任务只查一次）+ 本车偏移。
- `MoveAbsoluteAsync(x,y,z)` / `MoveRelativeAsync(dx,dy,dz)`：内部取整并校验成功。
- `MagnetOnAsync()`（置边界）/ `MagnetOffAsync()`。
- `SetCraneSpeedAsync()`。
- `WaitCraneAsync(predicate, 描述)`：**实时**读 `ICraneDriver.ReadStatusAsync`（天车无后台采集）轮询到条件成立；读到 `HasAlarm` 立即抛、超时抛异常。
- `WaitDeviceAsync(device, 点名, 期望)`：轮询**采集器写入的缓存快照 `device.Signals`**（**不实时读 PLC**，避免与 `DeviceStateCollector` 争连接）；**信号缺失视为"未知、不满足"**（不能把"没采到数据"当成"无料"，尤其 `期望=false` 时），超时抛异常。
- `WriteDeviceAsync(device, 点名, 值)`。
- 其他公开成员：`Crane` / `Workpiece` / `Options`（本任务一份） / `HasPieceOnCrane`（仅用于异常提示） / `CraneDriver` / `DeviceDriver(deviceId)`。
- `LogStep(设备, "<阶段>：<动作>")` / `LogStep("…")` / `LogStepWarn("…")`：写**流程步骤日志**，
  自动带 `[天车] 工件 <版号>/<序号>`（带设备时再加 `[设备名]`），用来把下面的原语日志串成"到哪一步、在哪台设备上"（见 §11）。
- 超时统一用 `StateMachine.HandshakeTimeoutMs`（默认 60s，**每次等待独立计时**）；运动到位超时用 `Crane.MoveTimeoutMs`（驱动内部）。
- 轮询间隔写死 **200ms**（不在配置里）：`WaitDeviceAsync` 读**缓存快照**、`WaitCraneAsync` **实时读天车 PLC**；
  `WaitCraneAsync` 若读到 `HasAlarm`（伺服/PLC 报警任一非 0）**立即抛异常，不等超时**。

### 5.5 六个设备 handler
`ITransferHandler`（`CanHandle` / `PickAsync` / `PlaceAsync` / `ClearHandshakeAsync`）由 `TransferHandlerRegistry` 按 `DeviceType` 分派：
`LoadRackHandler`、`BoringHandler`、`LatheHandler`、`GrinderHandler`、`MarkerHandler`、`UnloadRackHandler`。

**握手位复位 `ClearHandshakeAsync`（尽力清）**
双头镗/斜床/研磨机的握手位是**电平**信号（上位机写 1 后一直保持），机器侧靠它们判断"上位机已完成某一步"；
**残留 1 会让下一轮上料收不到上升沿**。约定：编排器在中转时**清两侧、先源后目标**——
**先清源**（设备作为源完成取料后，清掉刚写出的"下料完成"等位；此刻距写下已隔整段 XY 移动，PLC 必然已采到那个 1）、
**再清目标**（作为目标开始放料前，清掉上一轮残留，保证放料阶段写 1 是干净的 0→1 上升沿）：

| handler | 复位的点名（写 0） |
|---|---|
| `BoringHandler` | `DataSentDone`(12205)、`LoadDone`(12209)、`UnloadDone`(12217) |
| `GrinderHandler` | `DataTransDone`(14623)、`LoadInPlace`(14625)、`LoadDone`(14627)、`UnloadInPlace`(14629)、`UnloadDone`(14631) |
| `LatheHandler` | `DataSentDone`(#1101)、`CraneLoadInPlace`(#1102)、`CraneLoadDone`(#1103)、`CraneUnloadInPlace`(#1104)、`CraneUnloadDone`(#1105) |
| 料架 / 打号机 / 下料架 | 无（空操作；打号机经现场确认无需复位） |

- **只清握手位、不清加工参数**：长度/直径/`#800`/`#909` 等下一轮上料必被重写，清 0 反而可能被机器读成中间态。
- **逐点容错**：单点写失败只记警告、不影响任务 —— 真清不掉最坏就是"残留 1"，退回清理前的行为。
- **放在中转而不是取料末尾**：此时距写下"下料完成=1"已隔整段 XY 移动（通常 1~3s），PLC 必然已采到那个 1，
  **无需额外延时**；且此刻正是"与源设备业务关系结束"（源预约也在同一处释放）。
- **源与目标两侧都清，顺序先源后目标**：源侧清掉刚写出的"下料完成"等位（此刻距写下已隔整段 XY 移动，
  PLC 必然已采到那个 1）；目标侧清掉**上一轮残留**，保证放料阶段每次写 1 都是干净的 **0→1 上升沿**——
  残留 1 会让机器收不到这次下发，白等到握手超时（60s）后统一中止（冷启动、上一轮失败中止后尤其常见）。
- 手动操作页的「清握手位」复用同一实现（异常中止后人工补清）。
- `ClearHandshakeAsync` 返回**成功复位的点数**（0 = 该类型无需复位）；`TransferHandlerRegistry.Get` 对**没有 handler 的设备类型**会抛 `NotSupportedException`。
  ⚠️ 装载时**不校验**"每个启用设备类型都有 handler"：若把货叉/动平衡/验点这类**没有 handler** 的设备启用成**目标**，
  抛点会落在取料**之后**（板已在天车上）→ 直接变成一次故障暂停弃板（见 §12）。

## 6. 状态机公共骨架（每条流程一致）

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 原子获取 | `TryAcquire` 路权（区间 `[min(源,目标)−w/2, max(源,目标)+w/2]`）+ `TryReserve` 源/目标设备；**天车忙不在这里体现**——调度只读 `Crane.IsIdle` 选车，`State=Reserved` 是 Worker 出队时才置（见 §4、§9） |
| 2 | 审核源 | 内存一致（源设备 `CurrentWorkpiece` **非空时必须等于本任务**——为 null 放行；上料架队列除外）+ 等源 PLC 信号（各设备不同，见下） |
| 3 | 设置速度 | `SetAbsoluteSpeedAsync(X/Y/Z 速度/加减速度)`（来自 `CraneConfig`） |
| 4 | XY→source | 目标 = 设备库 X/Y **+ 本车偏移**；Z 用 `Crane.SafeZ`（**不加偏移**）。**斜床在这一步就已做 −YOffset**（直接绝对移动到二次偏移位），源特有阶段的 `+YOffset` 是把它送回库位 |
| 5 | Z 下降 | 目标 = 设备库 Z **+ 本车偏移 − ZDrop**（`ZDrop` 见 §8） |
| 6 | 感应有板 | 读天车 `X11`（`CraneStatusDto.HasPlate==true`） |
| 7 | 充磁 | `MagnetOnAsync`（轮询 X6）；此点即置"已吸板"边界 |
| 8 | 源特有动作 | 见下（含各自 Z 回升时机） |
| 9 | XY→target | 目标 = 设备库 X/Y **+ 本车偏移**；Z 用 `Crane.SafeZ` |
| 10 | 释放源预约 + 缩小路权 + **复位源与目标握手位** | `ReleaseSource` + `Resize` 到 `[targetX−w/2, targetX+w/2]` + `ClearHandshakeAsync`（先源后目标，见 §5.5） |
| 11 | 审核 target | 读目标 PLC 信号（请求数据/空闲/无板） |
| 12 | 下发参数 + 下发完成 | 按设备类型写参数并写"数据下发完成/传输完成=1"（**打号机、下料架无**该位） |
| 13 | 读请求上料 | 双头镗/斜床/研磨需要；打号机、下料架**无** |
| 14 | Z 下降 | 同步骤 5 |
| 15 | 目标特有动作 | 见下（放磁之前） |
| 16 | 放磁 | `MagnetOffAsync`（轮询 X7） |
| 17 | Z 回升安全 | 用 `Crane.SafeZ`（**不加偏移**） |
| 18 | 写上料完成 | 除下料架外都写 |
| 19 | X 回安全位 | 用 `Crane.SafeX`（**不加偏移**） |
| 20 | 释放 + 完成 | 释放路权 + 目标预约 + 天车锁；`TaskState`（下料→Completed，否则 Waiting） |

**源特有动作（步骤 8）**
| 源 | 步骤 |
|---|---|
| 上料架 | （无）→ Z 回升 |
| 双头镗 | Z 回升 → 写"下料完成=1" |
| 斜床 | 写"天车下料到位=1" → 读"尾座分开=1" → 相对 Y 回库位(+YOffset) → Z 回升 → 写"天车下料完成=1" |
| 研磨机 | 写"下料到达松开位置=1" → 读"松开完成下料退出=1" → Z 回升 → 写"下料完成=1" |
| 打号机 | Z 回升 → 写"下料完成=1" |

**目标特有动作（步骤 15，放磁之前）**
| 目标 | 步骤 |
|---|---|
| 双头镗 | （无） |
| 斜床 | 相对 Y 偏移(−YOffset) → 写"天车上料到位=1" → 读"尾座夹紧=1" |
| 研磨机 | 写"上料到达锁紧位置=1" → 读"锁紧完成上料退出=1" |
| 打号机 | （无） |
| 下料架 | （无） |

## 7. 五条流程逐步详解

> 公共步骤按 §6 展开；下面给出**每一步读了什么、写了什么**。坐标均"设备库值 + 本车偏移"（Z 下降再减 `ZDrop`；安全位不加偏移）。

### 7.1 上料架 → 双头镗
1. 获取：路权 + 预约上料架/双头镗。
2. 审核源：等上料架 `HasMaterial=1`（FC02 输入线圈）。
3. 设置天车速度（X/Y/Z 速度/加减速度）。
4. XY 到上料架：`(上料架X+OffsetX, 上料架Y+OffsetY, SafeZ)`。
5. Z 下降：`上料架Z+OffsetZ − ZDrop(上料架,直径)`。
6. 读天车 `X11=1`（有板）。
7. 充磁（`MagnetOnAsync`；边界置位）。
8. （源无特有动作）Z 回升到 `SafeZ`。
9. XY 到双头镗：`(双头镗X+OffsetX, 双头镗Y+OffsetY, SafeZ)`。
10. 释放上料架预约；路权缩到 `[双头镗X−w/2, 双头镗X+w/2]`；**复位握手位（先源后目标）**：清上料架刚写出的位（上料架无写入位 → 空操作）、清双头镗上一轮残留（见 §5.5）。
11. 读双头镗 `请求数据=1`（`12203`）。
12. 写参数：长度 `4083`、直径 `4087`(×100)、左堵厚 `4089`(×100)、右堵厚 `4091`(×100)、内孔锥度 `4093`(×100)、内孔成活/版孔 `4095`(×100)、圆角 `4097`(×100)；写 `数据下发完成=1`（`12205`）。
13. 读 `请求上料=1`（`12207`）。
14. Z 下降：`双头镗Z+OffsetZ − ZDrop(双头镗,直径)`。
15. （目标无特有动作）。
16. 放磁（轮询 X7）。
17. Z 回升到 `SafeZ`。
18. 写 `上料完成=1`（`12209`）。
19. X 回安全位 `SafeX`。
20. 释放路权 + 双头镗预约 + 天车锁；工件 `TaskState=Waiting`（继续下一段）、位置=双头镗。

### 7.2 双头镗 → 斜床
1. 获取：路权 + 预约双头镗/斜床。
2. 审核源：读双头镗 `请求下料=1`（`12215`）。
3. 设置天车速度。
4. XY 到双头镗。
5. Z 下降。
6. 读 `X11=1`。
7. 充磁。
8. 源特有：Z 回升 → 写双头镗 `下料完成=1`（`12217`）。
9. XY 到斜床。
10. 释放双头镗预约；路权缩到斜床区间；**复位握手位（先源后目标）**：清双头镗刚写出的位、清斜床上一轮残留（见 §5.5）。
11. 读斜床 `请求数据=1`（宏 `#1001`）。
12. 写参数：`#800 长度`、`#801 成活直径(Diameter)`、`#802 堵孔尺寸/版孔类型(PlugHole)`、`#909 加工模式 = 工件「斜床工艺」`（`WorkpieceInfo.LatheMachiningMode`，**1~10，按录入值原样下发，不再写死 1**）；写 `#1101 数据下发完成=1`。
13. 读 `#1002 请求上料=1`。
14. Z 下降：`斜床Z+OffsetZ − Round(直径/2)`（斜床用半直径公式）。
15. 目标特有：相对 Y 偏移 `−YOffset`（读当前坐标后相对移动）；
16. y相对移动完成后 写 `#1102 天车上料到位=1`；读 `#1003 尾座夹紧=1`。
17. 放磁。
18. Z 回升到 `SafeZ`。
19. 写 `#1103 天车上料完成=1`。
20. X 回安全位。
21. 释放；位置=斜床。

> `YOffset = Round((顶尖距离 − 工件长度)/2 + 孔径偏移)`，大孔(PlugHole=100)→122、小孔(70)→55；参数**每台斜床一份**（`App:Transfer:Lathes:<设备号>`）。

### 7.3 斜床 → 研磨机
1. 获取：路权 + 预约斜床/研磨机。
2. 审核源：读斜床 `请求下料=1`（`#1004`）。
3. 设置天车速度。
4. XY 到斜床，**Y 取"二次偏移位置" = 库位Y+OffsetY − YOffset**。
5. Z 下降：`斜床Z+OffsetZ − Round(直径/2)`。
6. 读 `X11=1`。
7. 充磁。
8. 源特有：写 `#1104 天车下料到位=1` 
9. 读 `#1005 尾座分开=1`
10.  相对 Y `+YOffset` 回库位 
11.  Z 回升
12. 写 `#1105 天车下料完成=1`。
13. XY 到研磨机。
14. 释放斜床预约；路权缩到研磨机区间；**复位握手位（先源后目标）**：清斜床刚写出的位、清研磨机上一轮残留（见 §5.5）。
15. 读研磨机 `请求数据=1`（`14603`）。
16. 写参数：版辊直径 `14633`、版辊长度 `14637`、加工模式 `14635`（`PlugHole==100?1:2`，1=大孔/2=小孔）；写 `数据传输完成=1`（`14623`）。
17. 读 `请求上料=1`（`14605`）。
18. Z 下降：`研磨机Z+OffsetZ − Round(直径/2)`。
19. 目标特有：写 `上料到达锁紧位置=1`（`14625`）→ 读 `锁紧完成上料退出=1`（`14607`）。
20. 放磁。
21. Z 回升到 `SafeZ`。
22. 写 `上料完成=1`（`14627`）。
23. X 回安全位。
24. 释放；位置=研磨机。

### 7.4 研磨机 → 打号机
1. 获取：路权 + 预约研磨机/打号机。
2. 审核源：读研磨机 `请求下料=1`（`14609`）。
3. 设置天车速度。
4. XY 到研磨机。
5. Z 下降：`研磨机Z+OffsetZ − Round(直径/2)`。
6. 读 `X11=1`。
7. 充磁。
8. 源特有：写 `下料到达松开位置=1`（`14629`）→ 读 `松开完成下料退出=1`（`14611`）→ Z 回升 → 写 `下料完成=1`（`14631`）。
9. XY 到打号机。
10. 释放研磨机预约；路权缩到打号机区间；**复位握手位（先源后目标）**：清研磨机刚写出的位、清打号机上一轮残留（打号机无写入位 → 空操作，见 §5.5）。
11. 读打号机 `设备空闲`：**0001 的 0 才表示空闲**（FC04，点名 `Busy`），即等 `Busy=false`。
12. 写：打印内容（FC16，`PrintContent`）、**外径=`Diameter`（工件直径）**、**内径=`PlugHole`(70/100)**（FC06）。
13. **无**请求上料。
14. Z 下降：`打号机Z+OffsetZ − ZDrop(打号机,直径)`。
15. （目标无特有动作）。
16. 放磁。
17. Z 回升到 `SafeZ`。
18. 写 `上料完成=1`（FC06 `LoadDone`）。
19. X 回安全位。
20. 释放；位置=打号机。

### 7.5 打号机 → 下料架
1. 获取：路权 + 预约打号机/下料架。
2. 审核源：读打号机 `加工完成=1`(0003地址)（FC04 `ProcessDone`）。
3. 设置天车速度。
4. XY 到打号机。
5. Z 下降：`打号机Z+OffsetZ − ZDrop(打号机,直径)`。
6. 读 `X11=1`。
7. 充磁。
8. 源特有：Z 回升 → 写 `下料完成=1`（FC06 `UnloadDone`）。
9. XY 到下料架。
10. 释放打号机预约；路权缩到下料架区间；**复位握手位（先源后目标）**：清打号机刚写出的位（打号机无写入位 → 空操作）、清下料架上一轮残留（下料架无写入位 → 空操作，见 §5.5）。
11. 读下料架 `无板`（`HasMaterial==false`，FC02 输入线圈 bit1）。
12. **无参数**。
13. **无**请求上料。
14. Z 下降：`下料架Z+OffsetZ − ZDrop(下料架,直径)`。
15. （目标无特有动作）。
16. 放磁。
17. Z 回升到 `SafeZ`。
18. **无**上料完成（现场暂不需要写放料完成脉冲）。
19. X 回安全位。
20. 释放；工件 `TaskState=Completed`、位置=下料架。

## 8. 坐标与参数换算

### 8.1 坐标
```
baseX = 设备库 PositionX + 本车 OffsetX
baseY = 设备库 PositionY + 本车 OffsetY
baseZ = 设备库 PositionZ + 本车 OffsetZ

Z 下降目标 = baseZ − ZDrop(设备类型, 直径)
Z 回升/SafeZ = 本车 Crane.SafeZ（不加偏移）
X 回安全    = 本车 Crane.SafeX（不加偏移）
```
- `ZDrop`：斜床/研磨 = `Round(d/2)`；其余设备 = `Round((d/2)/0.9537 + (d/2)/0.866)`。
- 设备坐标**运行期现查数据库**（`IConfigurationStore`）；天车偏移量来自 `CraneConfig.OffsetX/Y/Z`。

### 8.2 加工参数下发（按目标设备类型）
| 设备 | 参数 |
|---|---|
| 双头镗 | 长度`Length`；直径/左堵厚/右堵厚/内孔锥度/内孔成活或版孔/圆角 **×100**；写"数据下发完成" |
| 斜床 | `#800 长度`、`#801 成活直径`、`#802 堵孔尺寸/版孔类型`、`#909 加工模式(工件「斜床工艺」1~10)`；写"数据下发完成" |
| 研磨机 | 版辊直径`Diameter`、版辊长度`Length`、加工模式`PlugHole==100?1:2`；写"传输完成" |
| 打号机 | 打印内容`PrintContent`；外径`Diameter`、内径`PlugHole` |
| 下料架 | 无 |

## 9. 资源与并发

- **路权**（`RightOfWayManager`）：一个在途任务 = 一个 X 区间锁；任务开始时 `TryAcquire`（相交即失败→回滚），
  到目标 `Resize` 缩小到车体区间（`XInterval.FromTask(x, x, w)`），完成回安全位后 `Release`。
  ⚠️ `Resize` 的返回值目前**被忽略**（缩小失败时无日志、宽区间继续占着）。
- **设备预约**（`ResourceReservationManager`）：`TryReserve(源,目标)` 整体原子；到目标 `ReleaseSource` **只放源**；
  完成 `Release` 释放**本任务剩余的全部**（目标，以及仍持有的源——带**归属校验**，绝不误删别人的预约）。**不做超时回收**（释放由状态机保证）。
- **任务状态**（`WorkpieceRuntime.TaskState`）：`Waiting→Assigned` 由 `WorkpieceRuntime.TryTransition` 内部的
  `Interlocked.CompareExchange` 原子迁移、**只成功一次**。
- **派发期只做非原子预判**：调度器只 `CanAcquire`（路权区间是否空闲）与 `IsReserved`（源/目标是否被预约），
  **真正加锁在状态机的 `Acquire`**（`TryAcquire` + `TryReserve`）；两者之间存在窗口，被抢先时状态机回滚回 `Waiting`、下轮重派——这就是"下轮重试"的来源。
- **任务交接**：per-crane `Channel<TransportTask>`（容量 1）。注意 `Crane.Runtime.State=Reserved` **不在派发时置**，
  而是 Worker 出队时置；同一候选被重复派给同一台车，靠"容量 1 + `TryWrite` 失败回退换车"兜住。
- **`Crane.Runtime` 的写者**：**只有该车的执行线程**（Worker 及其调用的状态机、`TaskAbortCoordinator` 都在同一线程）；
  调度器**只读、从不写**（v2.41 起）。
- ⚠️ **配置重载会排空任务队列**：`ConfigurationLoader.LoadAsync` 会调 `CraneTaskChannels.Clear()`；
  此时**已被 CAS 置为 `Assigned` 的工件没有回收路径**（生成器只处理 `Waiting`，也没有超时回收）→ 会一直停在"已派发"直到人工删除。
  规避办法就是操作规程：**改配置必须停线、改完关程序重开**（见《架构设计文档》§14.3）。
- **异常（统一，不分充磁前后）**：状态机流程内任何异常 → `TaskAbortCoordinator.Abort`（`Release(taskId)` 幂等，源若已 `ReleaseSource` 不会重复释放）：
  1. 释放路权 + 释放源/目标设备预约；
  2. 释放天车状态（`CurrentTask=null / State=Idle / LockedInterval=null`）；
  3. 清理：清天车与源/目标内存引用；把该工件标记为 `Discarded`（**保留记录便于追溯，不删除**）；
  4. **暂停线路** + 写 `statemachine.txt`/`alarm.txt` + **弹窗**（天车/设备/工件/步骤/原因）。
  - 目的：重启线路后只要 PLC 信号正确即可继续，不受残留任务影响。
  - **注意**：`Acquire` 失败（路权/预约竞争拿不到）**不是异常**，走 `Rollback`（任务回 `Waiting`、不暂停），下轮重派。

### 9.1 异常弹窗（UI 侧）
- 弹窗来源：`AlarmManager.Raised` 事件（后台线程触发）；UI（`App`）订阅后对 `Error` 级弹 `MessageBox`，内容含来源与系统动作。线路此时已 `PausedByFault`。

## 11. 日志（Application 层）

运行日志按类别落盘（`FileAppLogger` → `Logs/yyyy-MM-dd/<category>.txt`），高低频循环用 `Sample` 节流：

- **`Scheduling`**：**周期"调度开始/完成"**（候选池数、启用天车数、本轮派发数、**耗时**；**仅候选池非空时**才打，约每 10s 一对，轮数按周期自动换算，避免 0.5s 一轮刷爆）、
  **派发**（工件/任务短号/源→目标/天车/区间）、**逐项否决原因**（见下条）。
- **`Generation`**：**周期"生成开始/完成"**（入线任务数、上料队头、候选数、**耗时**；**仅线路运行中**时打，同样约每 10s 一对）、
  **逐项否决原因**（见下条）、走完（实际文案 `工件 X 已无可执行工序，标记完成`，并**同时**写一条 `Task` 日志 `任务完成：工件 X（后续已无可执行工序）`）。
- **「为什么这个设备 / 天车 / 任务不行」怎么查（两个文件共用同一机制 `ReasonChangeLog`）**：
  候选生成与调度每 0.5s 重算一遍否决原因，但**只在原因变化时落盘**——首次立即写、变化再写、不变静默、
  恢复写一条"已恢复"；同一对象设最小间隔（复用 `Logging.SampleSeconds`，默认 20s）防原因抖动刷屏；
  并且**只要本轮有对象被排除就报**，不必等"全军覆没"：
  - 生成：`工件 P1/1 无候选：源不可用（设备 斜床1 报警）`、
    `工件 P1/1 下一道 Boring(BoringMachine) 目标筛选：双头镗2:已被预约（另有 1 台可用，已生成候选）`；
  - 调度：`候选 P1/1 双头镗→斜床 天车筛选：天车1:忙，天车2:范围不覆盖（可执行 1 台）`、
    `候选 P1/2 … 暂未派发：源/目标设备已被其他任务预约（2 台可执行天车均冲突，下轮重试）`；
  - 恢复：`工件 P1/1 已恢复（上一轮原因：斜床1:报警）`（滞后约 1 轮，因为要等"没问题的那一轮"跑完才能判定）。
- **`StateMachine`**（含天车 + 工件 + 坐标/点名，异常带**步骤 + 原因 + 堆栈**）：
  - 任务开始/完成：`[天车] 任务开始/完成：<版号/序号> <源>→<目标>`；
  - 每步原语：设置速度、绝对运动`→X.. Y.. Z..`、相对运动`dX.. dY.. dZ..`、充磁/放磁、等待天车条件、等待设备信号`设备.点名=期望`、写设备`设备.点名=值`；
  - **步骤日志**（`ctx.LogStep(设备, "<阶段>：<动作>")`，写在每个 handler 的 `PickAsync`/`PlaceAsync` 内部
    与状态机的 `Acquire`/`TransitAsync`/`FinishAsync` 内部）：形如
    `[天车1] 工件 P1/1 [双头镗] 取料：Z 下降到取料位（Z=520，工件直径 320）`，
    把上面那些原语日志串成"**到哪一步、在哪台设备上**"，现场看日志即可判断卡在取料还是放料的哪一步；
  - **命名约定（全项目一致）**：所有与任务相关的日志行都以 `[天车名] 工件 <版号>/<序号>` 开头（设备相关的再带 `[设备名]`），
    因此**看任意一行就知道是哪块板**；搬运任务的随机 GUID 只以 **8 位短号**出现（如 `任务 8f3a1b2c`），
    仅用于与 `scheduling.txt` 的派发行对齐（派发行也是 8 位短号）；
  - 异常：`[天车] 任务 <版号/序号> <源>→<目标> 步骤[<阶段(设备)>] 异常：<原因>`（阶段如"取料(斜床1)/中转/放料(双头镗)/收尾"）。
- **`Collection`**：采集循环 —— 每周期心跳（`Sample`，默认 20s 一条）+ **逐台采集失败**
  （按设备号 `Sample` 节流，含"失败后 `IsConnected=false`、`Signals=空快照`"）。采集失败归此文件而非 `Communication`：
  后者只留**通信层**（连接/重连/读写失败、天车坐标抽样），两者分工为"采集循环看到了什么"vs"通信本身怎么了"。
- **`Task`**：**任务生命周期一条时间线** —— 创建（`RuntimeTaskManager.Add`）/ 开始（入线，含入线顺序号）/
  暂停 / 完成（送到下料架，或线上已无可执行工序）/ 丢弃（异常中止，带原因）。
  排查某块板只看这一个文件即可，不必在 `operation`/`scheduling`/`statemachine` 之间来回找。
- **`Communication` / `Operation`**：驱动层读写与天车动作（CraneService/Modbus）；操作日志含页面启停、添加任务、手动操作。

> 排查一次失败任务时，用工件版号/序号在 `statemachine.txt` 里可直接串起"派发→每步运动/信号→异常步骤"。派发记录在 `scheduling.txt`。

## 12. 异常 / 暂停 / 弹窗（统一，不分充磁前后）

**触发**：状态机流程内任何异常——运动不到位、握手信号超时、天车报警等。
其中**运动类**原语在 `!IsSuccess` / 超时 / 报警时抛 `InvalidOperationException`；
而**写点位** `WriteDeviceAsync` 是驱动直接写、**没有结果码、也不回读校验**，写失败只能靠随后的握手等待超时暴露。handler 一律不吞异常。

**处理**（`CraneStateMachine` 的 `catch` → `TaskAbortCoordinator.Abort`）：
1. 释放路权 `RightOfWayManager.Release(taskId)`；
2. 释放设备预约 `ResourceReservationManager.Release(taskId)`（**归属校验**：只删本任务仍持有的源/目标；源若已在 Transit 释放并被他车预约，绝不误删）；
3. 释放天车状态：`CurrentTask=null / State=Idle / LockedInterval=null`，并**无条件清空** `crane.CurrentWorkpiece`；
4. 清理：清源/目标 `CurrentWorkpiece`（**仅当正是该工件**，带归属校验）；把工件 `TaskState=Discarded`、`CurrentLocation=Discarded`（**保留记录，不删除任务**）；
5. `LineControlService.EnterFaultPause()`（暂停线路）；
6. `AlarmManager.Raise(Error, 天车名, 详情, 系统动作, 天车号, isCrane)` → 写 `alarm.txt`（`>= Error` 记 ERROR、否则 WARN，**类别都是 `Alarm`**）+ 触发事件。
   内存 `ActiveAlarmStore` 对"**同级别 + 同来源 + 同内容**"会**合并计数**，但**弹窗每次都弹**。
7. 写一条 `Task` 日志到 `task.txt`：`任务丢弃：工件 <版号>/<序号>（任务 <8 位短号>），天车 <名>，原因：…`
   （任务**保留在表里**不删除，便于只用 `task.txt` 追这一块板）。

> 步骤 1~4 在 `try` 内，**暂停与报警在 `finally`** —— 即使清理本身抛异常，也一定会暂停线路并报警。

**弹窗**：`AlarmManager.Raised` 事件（后台线程）；UI（`App`）订阅，对 **`Error` 及以上**（含 `Critical`）用 `Dispatcher` 弹 `MessageBox`，
标题"线路异常（已暂停）"，内容含：异常详情（天车/工件/源→目标/步骤/原因）+ 来源 + 系统动作 + 时间。

**不是异常**：`Acquire` 时路权/预约**竞争拿不到** → `Rollback`（任务回 `Waiting`、不暂停、不报警），下轮重派。

**兜底**：`CraneWorker` 的 `catch` → `FallbackAbort`（**只在 `crane.Runtime.CurrentTask` 仍非空时**才再调一次 `Abort`）。
正常异常路径下状态机的 `catch` 已经 `Abort` 过、`CurrentTask` 已被清空 → **不会二次 Abort**；
它真正覆盖的是"异常逃出状态机 `try`"的情况（`找不到工件任务 / 源或目标设备不存在`，发生在 `Acquire` 之前 → 本来也没有资源可漏）。

**成功路径**也写 `task.txt`：`任务完成：工件 <版号>/<序号>（已送到下料架）`（见 §11 的 `Task` 类别）。

## 14. 状态与数据速查

**`WorkpieceState`**：`Created`(未启动) → `Waiting`(已启动/排队) → `Assigned`(已派发) → `Running`(执行中) → `Waiting`(下一段) / `Completed`(下料完成，**或生成器判定"后续已无可执行工序"**)；`Paused`(人工暂停)；`Discarded`(异常中止弃板，由 `TaskAbortCoordinator` 置，任务**保留在表里**便于追溯，不删除)。

**`WorkpieceRuntime.CurrentLocation`**（唯一事实来源，仅状态机取/放料确认时写；异常中止时由 `TaskAbortCoordinator` 置 `Discarded`）：
`Queue` / `OnCrane(craneId)` / `AtDevice(deviceId)` / `Discarded`
（`WorkpieceLocationKind` 编号有空洞：`Queue=0` / `Device=1` / `Crane=2` / `Discarded=4`，**3 未使用**）。

**`TransportTask`**：`WorkpieceRuntimeId`、`Source/TargetDeviceId`、`SourceX/TargetX`、`TargetProcess`、`Priority`；区间由 `GetRightOfWayInterval(crane.Width)` 现算。

**`CraneState`**：`Idle` / `Reserved` / `Running`（只保留实现中**真正会赋值**的三种）。

**`Crane.Runtime`**：`CurrentTask` / `State` / `LockedInterval`，**只有该车执行线程写**（Worker + 其调用的状态机/Abort，同一线程），调度器只读不写。

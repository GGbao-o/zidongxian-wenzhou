## 2. 项目背景与目标

### 2.1 系统定位

本系统是一条**固定工艺自动产线**的上位机调度系统。上位机不直接做运动控制，而是承担"大脑"与"监视器"的角色：

- 从 PLC 采集设备与天车状态
- 在内存中维护工件任务与运行状态
- 计算工序之间的搬运任务
- 统一调度多台天车完成工件搬运
- 提供配置、监控、大屏、报警等页面

天车本身的 XYZ 三轴运动由天车 PLC 内部完成，上位机只负责把目标位置和动作指令写成 PLC 数据，再读回执行结果。 

### 2.2 系统本质

> 本系统不是"设备控制系统"，而是**工件在固定工序间的流转编排 + 多天车区间路权互斥**。

理解这句话非常关键：

- **不是设备控制**：真正的电机、伺服、限位、加减速曲线都在 PLC 里，上位机不参与
- **是流转编排**：工件从上料架出发，按固定工艺依次经过各设备，每一段由一个搬运任务完成
- **是区间互斥**：多台天车的活动范围相邻且略有重叠（交叉区），必须保证同一时刻不会有两台天车进入冲突的 X 区间

真正的难点不在单个设备，而在于三件事：

1. **工件身份跟踪**：工件没有贴条码，系统只能靠内存中的对象引用在设备与天车之间转移来"记住"它
2. **多车路权**：天车范围重叠，必须靠区间锁保证不撞
3. **异常后状态一致性**：通信中断、报警、超时发生时，内存状态和现场实物必须尽量对齐

因为系统是单进程、内存运行态、任务不落库，所以完全不需要微服务、消息队列、CQRS 等重型方案。固定产线用一套干净的分层架构就足够了。

### 2.3 设计目标

| 目标 | 说明 |
|---|---|
| 高内聚低耦合 | 分层清晰，层与层通过接口解耦，换协议不改业务 |
| 单一事实来源 | 每个状态只有一个权威来源，避免多处重复导致分歧 |
| 可重算 | 候选任务随时可基于当前状态重建，不维护脆弱的任务队列 |
| 安全 | 异常时程序自动清理内存并放弃该工件；现场残留实物只是不排产，不产生死锁、无需人工解 |
| 可维护 | 新设备类型通过策略扩展，不改调度主体 |
| 可模拟 | 未接 PLC 时可用模拟驱动跑通全流程，降低开发与联调风险 |

## 3. 需求分析

### 3.1 物理产线

一条笔直的线路。地面设备可能包括（依车间实际情况在数据库配置，**允许缺失**）：

```
上料架 → 货叉 → 双头镗 → 斜床(N台) → 研磨机(N台) → 动平衡机 → 打号机 → 验点机 → 下料架
```

需要强调几点：

- 设备不是固定的，不同车间可能没有其中某几台
- 哪些设备存在、有几台，全部通过数据库配置，程序不写死
- 同类设备可能有多台（斜床 N 台、研磨机 N 台），调度时需要选择具体哪一台

### 3.2 天车

龙门架上安装若干台天车（典型为三台），用于在设备之间搬运工件。

- 每台天车有可配置的**活动范围**，例如 30m 车间：
  - 天车 1：0 ~ 10000
  - 天车 2：8000 ~ 20000
  - 天车 3：18000 ~ 30000
- 活动范围是数据库配置，**不是写死的**
- 相邻天车的活动范围存在**交叉区**（如天车1和天车2在 8000~10000 重叠）
- 天车运动为 XYZ 三轴：XY 移动到目标位置 → 取板 → 送往下一工序
- 天车**不使用运动控制卡**，上位机只向 PLC 发送数据
- 天车有物理宽度，宽度也存放在数据库中，用于计算路权区间

> **关于交叉区与碰撞**：本系统**不做动态避让**，而是采用「**任务区间路权互斥**」——一个任务在执行前先把它所涉及的 X 区间整段锁住，其它天车若任务区间与之相交，则本周期不执行、重试。这样从机制上保证两台天车不会同时进入冲突区间。详见第 8.7 节。

| 页面 | 功能 |
|---|---|
| 主页面 | 启动线路；添加任务（弹窗录入工件信息）；当前任务显示栏（工序/下一工序/暂停/清除） |
| 天车管理 | 天车配置（ID/序号/名称/协议/IP/端口/各轴速度/加减速/StartX-EndX 等）；运行状态监控 |
| 设备管理 | 设备配置；实时 XYZ 坐标、加工长度、信号、当前工件 |
| 工序管理 | 流程顺序（固定工艺，v1 只读展示） |
| 参数设置 | 程序参数（周期、超时、日志等），存 appsettings.json |
| 大屏展示 | 设备/天车信号、颜色状态、悬浮显示工件信息、当前锁定区间与可执行任务 |
| 报警处理 | 报警内存展示 + 磁盘日志；异常由程序自动清理，不设"人工清内存/解死锁"按钮 |
| 手动操作页面 | 选择天车进行手动操作 并且可以读取信号 |

### 3.4 关键约束

| 约束 | 说明 |
|---|---|
| 工件任务不落库 | 工件信息只存内存，程序关闭即消失（**刻意设计**） |
| 报警不落库 | 报警只写磁盘日志 + 内存，页面直接读内存 |
| 数据库只存配置 | 只保存天车、设备、工艺路线等配置，**不保存**任务与报警运行态 |
| 信号点位不进库 | 设备/天车的信号地址、数据类型、读写权限**定义在代码类中**，不进数据库 |
| 任务丢弃式异常处理 | 天车状态机异常时直接丢弃当前任务、释放全部逻辑锁、清空相关内存状态，避免死锁 |
| 工艺固定 | v1 页面不允许修改流程；完整工艺路线以现场确认为准 |
| 暂不接 PLC | 当前阶段不接现场 PLC，先以接口 + 模拟驱动开发验证 |

### 3.5 设计难点与风险

#### 难点 1：异常废弃后工件身份丢失（已确认策略）

工件信息仅存内存，且实物没有条码/RFID 标识。异常丢弃任务后，若实物仍卡在设备或天车上，其板号/序号/直径/长度将无从与实物关联（若删除内存记录则永久丢失；当前实现**保留 `Discarded` 记录**便于追溯）。

**已确认处理方式**：异常时程序自动清理并**把该工件标记为 `Discarded`**（见 §10.4），**无需操作员点击任何清障按钮**：

- 工件本身字段仍保留在内存（`Discarded` 记录，便于追溯），但已**脱离设备/天车引用**、不再参与生成
- 现场即使残留实物，也只是"有实物、无数据"，`TransportTaskGenerator` 不会为它生成任务
- 现场人员把实物取走即可；系统不会因此死锁

#### 难点 2：工件位置唯一事实来源

设备与天车都持有"当前工件"的引用，如果两边各自写状态就会产生分歧。解决办法是引入唯一的 `CurrentLocation`（见 §6.1），设备/天车的当前工件只是查询派生结果。

#### 难点 3：取放料成功判定

内存中的引用转移（`Crane.CurrentWorkpiece = WP`）必须由现场物理信号确认，否则会出现"系统以为搬走了、实际还在地上"的脱节。判定规则见 §8.10，前提是 PLC 能提供有料/无料等反馈信号。

#### 难点 4：多车区间互斥

天车范围重叠，若不互斥会相撞。本系统用「任务 X 区间锁」解决（见 §8.7）。之所以不需要复杂的动态避让，是因为：

- 任务结束后天车会回到**安全位置**
- 安全位置由现场设置，保证不在互斥区，也不会影响其它天车
- 因此空闲天车不占路权；路权在**状态机开始执行任务时**取得，天车回到安全位后释放

#### 难点 5：冷启动状态核对

启动时内存任务为空，但现场可能残留工件。处理方式见 §10.5 的"冷启动核对"。

### 4.2 分层职责与依赖规则

| 层 | 职责 | 依赖方向 |
|---|---|---|
| Presentation | 展示与交互 | 依赖 Application，不依赖 Infrastructure |
| Application | 业务编排与调度 | 依赖 Domain、Runtime Store、基础设施接口 |
| Domain | 纯业务对象，无外部依赖 | 不依赖任何层 |
| Runtime Store | 内存运行态容器 | 由 Application 持有与访问 |
| Infrastructure | 驱动、仓储、日志、配置 | 实现 Application 定义的接口，依赖 Domain |

**硬性规则**：

- Domain 不得引用 EF Core、PLC 库、WPF
- Presentation 不得出现 SqlConnection、驱动 SDK、状态机步骤操作
- Application 通过接口访问 Infrastructure，不直接 new 具体实现
- 状态写入遵循"单写者原则"（见 §12.3）

### 4.3 使用的设计模式

| 模式 | 位置 | 解决什么问题 |
|---|---|---|
| Layered Architecture | UI / Application / Domain / Infrastructure | 边界清晰、可替换 |
| Registry Pattern | DeviceRegistry、CraneRegistry | 保证设备/天车全局唯一实例 |
| Centralized Scheduler | CraneScheduler | 避免多车抢任务产生竞态 |
| Worker Pattern | CraneWorker（每台天车一个） | 集中分配、独立执行 |
| State Machine Pattern | CraneStateMachine | 机械动作分步、不阻塞 |
| Strategy Pattern | ITransferHandler（按设备类型） | 不同设备握手差异 |
| Snapshot Pattern | Signals 快照、CandidateTaskPool | 解决信号一致性与任务重算 |
| Reservation / Ownership | 设备预约 | 设备资源归属明确 |
| Interval Lock | RightOfWayManager | 天车 X 区间互斥、防撞 |
| Single Source of Truth | 工件唯一对象、位置唯一来源、预约唯一来源 | 避免状态分歧 |
| Single Writer Principle | Collector 写 Signals，该车 Worker 独占写 Crane.Runtime | 避免并发写 |
| Dependency Injection | 全模块通过接口注入 | 解耦、可测试 |

## 6. 领域模型（Domain）

领域模型只表达业务对象，不关心数据库、PLC 协议、页面。

### 6.1 工件模型

```
WorkpieceTask
├── WorkpieceInfo       工件自身数据（不变）
└── WorkpieceRuntime    运行状态（可变）
```

**WorkpieceInfo（只存工件自身数据，创建后不变）**

| 字段 | 类型 | 说明 |
|---|---|---|
| RuntimeId | Guid | 运行期唯一标识（内存生成，不落库） |
| PlateNo | string | 版号 |
| SerialNo | int | 序号 |
| Length | double | 长度 |
| Diameter | double | 直径 |
| LeftPlugThickness | double | 左堵厚 |
| RightPlugThickness | double | 右堵厚 |
| PlugHole | int | 堵孔：**只能 70 / 100**，70=小孔、100=大孔 |
| PrintContent | string | 打印内容 |
| InnerHoleTaper | double | 内孔锥度 |
| FilletSize | double | 圆角大小 |
| NeedBalancing | int | 是否做动平衡：**0=不需要、1=需要**。⚠️ 当前**仅作记录/展示、不参与路由**——去不去动平衡节点只由「有没有启用的动平衡机」决定（§13.4） |
| LatheMachiningMode | int | 斜床工艺（写入斜床宏 `#909` 加工模式）：**1~10**，默认 1；**编辑任务时不可改**（见 §13.1） |

> 工件自身数据当前就这些，后续可能增加或修改（字段以本节为准）。

**WorkpieceRuntime（只存运行状态，随流程变化）**

| 字段 | 类型 | 说明 |
|---|---|---|
| CurrentProcess | ProcessType（volatile） | 当前工序 |
| CurrentLocation | WorkpieceLocation | **位置唯一事实来源** |
| TaskState | WorkpieceState（volatile） | 任务状态，描述是否已启动/暂停/派发/执行中/完成/丢弃 |
| QueueOrder | int | 入线顺序号（上料架取板顺序），0 表示未入队（未启动/已暂停） |

**WorkpieceLocation（位置枚举，权威来源）**

```
Queue          在等待队列
Device(id)     位于某台设备上
Crane(id)      位于某台天车上
Discarded      已丢弃（异常）
```

> **位置唯一事实来源规则（重要）**
>
> 设备与天车的"当前工件"不得各自独立写状态。位置变化**只允许**由天车状态机在"取放料确认成功"的那一刻单点写入 `WorkpieceRuntime.CurrentLocation`；设备/天车的 `CurrentWorkpiece` 只是查询派生的结果或只读缓存，不作为权威状态。谁在什么时机写，见 §12.3 单写者原则。

### 6.2 设备模型

采用"**一个物理设备 = 一个运行时对象实例**"的方式。例如 `LatheMachine` 类会实例化出 `Lathe01 / Lathe02 / Lathe03`。

```
DeviceBase
├── Config              数据库配置（身份、连接、位置、能力）
├── Signals             PLC 当前快照
├── IsConnected         连接状态
└── CurrentWorkpiece    当前工件（只读派生）
```

> `ResourceState` 作为**领域字段已删除**（从不写入）；界面按事实派生（断开/报警/预约/在制），见 §13.6 与 §19.2。

**设备分类（按需扩展）**

| 类型 | 类 | 备注 |
|---|---|---|
| 上料架 | LoadRack | 仅上料，无加工 |
| 货叉 | ForkMachine | 是否参与搬运以现场为准 |
| 双头镗 | BoringMachine | |
| 斜床 | LatheMachine | N 台 |
| 研磨机 | GrinderMachine | N 台 |
| 动平衡机 | BalancingMachine | |
| 打号机 | MarkerMachine | 是否上线以现场为准 |
| 验点机 | CheckMachine | 是否上线以现场为准 |
| 下料架 | UnloadRack | 仅下料 |

**关于信号（Signals）**：设备点位（地址、功能码、读写、换算）定义在**驱动的点位表**里（`DeviceModbusMaps` / `LatheFocasDriver`），不进数据库；点位与 PLC 程序强耦合，属工程常量，放代码里便于版本管理。
采集器按点位表读**输入点位**，把 `点名=值` 放进 `device.Signals` 缓存；业务层/界面只读缓存，**不另建"信号目录"**（已删除 `DeviceSignalCatalog`/`SignalPoint`，避免与真实驱动点位对不上）。

### 6.3 天车模型

"**一台物理天车 = 一个 Crane 实例**"。

```
Crane01
├── Config              数据库配置（范围、宽度、速度、加减速、安全位、偏移等）
├── CurrentWorkpiece    当前工件（只读派生）
└── Runtime
    ├── CurrentTask     当前正式任务
    ├── State           天车状态
    └── LockedInterval  当前持有的路权区间（执行期间）
```

> **天车不后台采集、不存信号快照**：天车连接/报警/位置/X 区信号（含 `X11 有板`）一律**按需实时读** `ICraneDriver.ReadStatusAsync`，不存在 `Crane.Signals`（已删除）。

### 6.4 搬运任务模型

```
TransportTask
├── TaskId
├── WorkpieceRuntimeId   关联工件
├── SourceDeviceId       源设备
├── TargetDeviceId       目标设备
├── SourceX / TargetX    两端设备 X 坐标（用于计算路权区间）
└── Priority
```

### 6.5 工艺路线模型

```
ProcessRoute
└── ProcessNode[]
    ├── Process         工序枚举
    └── DeviceType      对应设备类型
```

> **节点不声明"必需/可选"**：某道工序是否参与工艺，由 `ProcessRoute.GetNextAvailable` 按
> 「该设备类型当前有没有启用设备」**现算**——没有设备的工序自动跳过；有设备的工序**必经**
> （设备离线/报警时工件会停下来等它，不会绕过去）。
> 该判据由 `ProcessRoute.AvailableDeviceFilter` 统一提供，生成器 / 主页面"下一道工序" / 工序展示页共用。

下一工序由 `ProcessRoute.GetNext(CurrentProcess)` **现算**，不持久化。工艺路线的最终内容以现场为准；
考虑到车间排布一旦确定就不再调换设备（仅坐标可能微调，坐标由 `DeviceConfig` 的 **X/Y/Z 绝对坐标**管理），
**工艺顺序固定在代码中**（`ProcessRoute` 内置默认顺序），不进数据库，避免多一处可能不一致的配置。
若将来确需运行期调整顺序，再改为表驱动。

### 6.6 路权区间值对象（XInterval）

```
XInterval
├── Min        区间左端（含）
└── Max        区间右端（含）
```

提供两个关键能力：

- `Overlaps(other)`：判断两个区间是否相交
- `FromTask(sourceX, targetX, craneWidth, safetyMargin)`：由任务两端设备坐标和天车宽度计算区间

具体计算规则见 §8.7。

## 7. 运行时内存层（Runtime Store）

所有运行任务**只存在内存**，程序关闭后消失，这是刻意的设计。

| 容器 | 职责 |
|---|---|
| RuntimeTaskManager | 全线工件任务内存总表（唯一） |
| DeviceRegistry | 全线唯一设备对象目录 |
| CraneRegistry | 全线唯一天车对象目录 |
| CandidateTaskPool | 当前理论可执行任务快照 |
| ReservationManager | 当前正式任务占用的设备资源 |
| RightOfWayManager | 当前已锁定的天车 X 区间集合 |
| ActiveAlarmStore | 当前活动报警 |

**Registry 示例**

```
DeviceRegistry
  1 → Fork01
  2 → Boring01
  3 → Lathe01
  4 → Lathe02
  5 → Grinder01
```

`DeviceRegistry.Get(3)` 永远返回**同一个** `Lathe01` 实例。这样就杜绝了"UI 显示一个 Lathe01、任务生成器又 new 一个 Lathe01"导致的状态不同步问题。

## 8. 应用服务层（Application）

应用服务层是整个系统的控制中心。每个服务都定义接口，通过 DI 注入。

### 8.1 LineControlService

| 职责 | 说明 |
|---|---|
| StartLine | 启动线路，恢复调度与 Worker |
| PauseLine | 请求暂停 |
| ResumeLine | 恢复运行 |
| EnterFaultPause | 故障暂停 |

启动流程：`StartLine()` → 冷启动核对（§10.5）→ Scheduler 恢复派发 → Worker 恢复运行。

### 8.2 DeviceStateCollector   

设备采集，启动程序就在跑。

- 周期（默认 500ms）**并发**读取所有**已启用**设备（只采设备）：每台一个 Task，`Task.WhenAll` **全部完成**后统一替换缓存
- 解析为完整 Signals 对象后**整体替换**，不逐字段更新
- 单台读取失败/超时**只放弃本台本周期**（写断开空快照），下周期再试；**不重连、不报警**
- 更新连接状态、判定快照是否过期
- **只采集，不调度，不发送工艺动作**

> 之所以"并发 + WhenAll"：顺序读时某台离线（连接超时）会串行累加拖死整周期；并发后整周期耗时 ≈ 单台最长耗时。
> 采集超时用 `Collection.CommunicationTimeoutMs`（Modbus；FOCAS 用自身默认）；失败不产生报警——**报警只来自异常（天车状态机等）**。

> **天车不后台采集**（v2.24）：天车的运动/到位由 `CraneService` 方法自身实时读取；
> 调度选车、状态机预检查、冷启动核对、大屏展示都**按需**调用 `ICraneDriver.ReadStatusAsync`，
> 避免后台轮询与运动轮询争抢同一条 Modbus 连接。

之所以要"整体替换"而不是"逐字段更新"，是因为逐字段更新在读取过程中可能出现前后不一致（读到一半状态变了）。整体替换保证同一份快照来自同一个采集时刻。

每份快照包含：

```
CapturedAt       采集时间
Sequence         递增版本
ConnectionState  Connected / Disconnected
Quality          Good / Stale / Bad
```

### 8.3 TransportTaskGenerator

候选任务生成 ：启动程序一刻就在跑了

每 500ms 根据当前内存状态与 PLC 信号**重建**候选任务池（Snapshot / Rebuild 模式，不是传统任务队列）：生成当前**理论上可执行的任务**，同一时刻可能同时存在多个（多个工件，或多台同类设备都能接收同一工件）。

计算依据：

```
工件在什么位置？
当前工序是什么？
下一工序是什么？
源设备是否具备出料条件？
目标设备是否空闲、连接正常、可加工、请求上料？
目标设备是否符合该工件加工范围（直径/长度）？
源/目标设备是否已被其他任务预约？（设备级；只读判断，真正预约在状态机执行时，见 §8.4/§8.6）
多台同类设备时按 tie-break 规则选择（§8.3.1）
```

> **没有"任务预约"这个概念**：系统的预约**只针对设备**。调度器派发时**只判断**源/目标是否已被别的任务预约；
> **真正的设备预约在状态机开始执行任务时**原子 `TryReserve`（§8.4/§8.6）。已派发/执行/完成的工件由
> `WorkpieceRuntime.TaskState` 拦住、不再生成候选。

输出仅为候选：

```
CandidateTask
  Workpiece → WP001
  Source    → Boring01
  Target    → Lathe02
  Priority  → 100
```

**候选任务不代表已派发，也不代表天车已开始搬运**。它只是"当前理论上可以做的事"。

**输出为全枚举**：一个工件 × 每个符合的目标设备 = 一个候选，**不截断、不预先选最优**。

```
CandidateTask[]
  WP001  Boring01 → Lathe01     Priority 100
  WP001  Boring01 → Lathe02     Priority 100
  WP001  Boring01 → Lathe03     Priority 100
  WP002  Lathe01  → Grinder01   Priority 100
  WP002  Lathe01  → Grinder02   Priority 100
```

- **只要符合条件的目标都要生成**；"选哪个"交给调度器（§8.4）。同一工件的多个目标在调度阶段**互为备份**：
  某个目标路权/预约拿不到时，自动改用下一个目标，而不是死等一个。
- 同类设备的"空闲、距离、负载"等只用于**候选排序（tie-break）**，不作为过滤或截断依据。

> **枚举模型是"每工件 的 源 × 目标"，不是全局任意组合**：源通常由**工件位置唯一确定**（工件在哪台设备，
> 源就是那台），所以"全枚举"是按**每个工件**枚举它的所有符合目标。
> 例：三个斜床各有一个工件、下一道都是研磨、两台研磨机都可上料 → 共 **6** 个候选（每个工件各 2 个），
> 而不是把 3 台斜床当成一个任务、任意选源。
>
> **唯一的多源情形**：工件在**队列（未上线）**时源 = 上料架；若启用**多个上料架**，才是真正的
> "上料架 × 目标" 笛卡尔积。
> 现状差异：`ResolveSource` 目前只取第一个启用的上料架（`FirstOrDefault`），**多上料架全枚举尚未实现**（见 §19.2）。

> **生成规则（已落地，详见《应用层设计.md》）**：
> 只在**线路运行中**生成（否则清空候选池）；只处理 `WorkpieceState.Waiting` 的工件（未启动/暂停跳过）；
> 源 = 工件所在设备（队列工件**只取队头**，队头 = 队列中 Waiting 且**入线顺序号最小**，源 = 唯一上料架）；下一工序取 `ProcessRoute.GetNextAvailable` 现算并**跳过无启用设备的节点**；
> 目标 = 同类型设备中满足 `<已连接、未预约、未报警、加工范围、放料就绪>` 者**全部枚举**。
> 源/目标"就绪"按设备类型读输入信号（`DeviceHandshakeRules`）：源 = 上料架有板 / 双头镗·斜床·研磨请求下料 / 打号加工完成；
> 目标 = 双头镗·斜床·研磨请求数据 / 打号空闲 / 下料架无板。

#### 8.3.1 候选排序与同类多设备 tie-break

生成阶段**只排序、不过滤**；排序依据同时也是调度器在同工件多目标间的 tie-break 顺序：

1. 加工范围匹配（直径/长度在设备能力内）——**硬过滤**；
2. 源/目标设备未被其他任务预约（**设备级**，非任务级）、非源自身——**硬过滤**；
3. 空闲、请求上料、连接正常、无报警——**排序优先**；
4. 距离最近（由源设备位置估算）；
5. 负载均衡（当前在制数量少者优先）。

> 已实现：候选按"每工件 × 每个满足条件的同类目标设备"**全枚举**；装配"源就绪/目标就绪"判定（`DeviceHandshakeRules`）。
> 上料架全系统唯一，队列工件只取队头。详见《应用层设计.md》。

### 8.4 CraneScheduler（集中式调度）

调度器常驻后台循环，按 `Scheduling.ScheduleIntervalMs` 周期运行。全系统只有一个调度器，统一决定"哪个任务 → 哪台天车"，而不是让每台天车自己去抢任务。集中调度的好处是：**不会出现两台天车同时抢到同一个任务**。

输入：

```
CandidateTaskPool
CraneRegistry
ReservationManager
RightOfWayManager
```

判断：

```
天车是否 Idle? 不需要判断是否在安全位置(就这么设计)
是否连接？
是否报警？
任务的源/目标 X 是否都在本天车 StartX/EndX 范围内？
任务 Priority？
距离？
两端设备是否已被别的任务预约？（只读判断）
路权区间是否空闲？（只读判断，不加锁；真正加锁在状态机执行时）
```

**派发流程（多任务 × 多天车分配）**：

每周期做一轮"任务 × 天车"分配，过程**单线程**，保证"判断"与"占用"之间没有竞态：

```
1. 算可执行矩阵：对每个候选任务，列出 StartX/EndX 覆盖源与目标、连接正常、无报警、Idle 的天车
2. 排序：候选按 Priority 降序 + **距离最近**（不做负载均衡）；天车按距离源最近
3. 贪心分配：依次取候选，从它的可执行天车中挑一台；**只判断、不加锁**：
     RightOfWayManager.CanAcquire(任务区间)        // 只读：区间是否空闲
     ReservationManager.IsReserved(Source/Target)  // 只读：设备是否已被别的任务预约
     都通过 → 派发：Crane.CurrentTask = TransportTask、TaskState = Assigned（不改任何锁）
     ← 任一不通过：换该候选的下一台天车（本周期），或下一轮换该工件的下一个目标候选；绝不死等
4. 本轮已占用的天车不再参与（一车一任务）；TaskState != Waiting 的工件不再生成候选
```

> **真正占用（加锁）在状态机执行时**：`TryAcquire`（路权）+ `TryReserve`（设备预约）由天车状态机开始执行任务时完成（见 §8.5/§8.7）；拿不到就回滚（释放天车锁、任务回 `Waiting`）下轮重派。

> **天车必须空闲**：正在执行状态机（`CurrentTask != null`）的天车**绝不再派任务**（硬约束）。
> 天车状态按需读（不做后台采集）。完整设计见《应用层设计.md》。

> **"不死等"的定义**：取不到路权只是**本周期不派发**——任务留在候选池，下周期用最新状态重算再试；
> 同一工件若还有别的目标、或还有别的空闲天车能执行，就在同周期内改试它们，而不是认准一个任务空等。

> **关于路权与竞态**：调度器派发时**只判断区间是否空闲**（不加锁）；**真正加锁在状态机开始执行时**，
> 由 `RightOfWayManager.TryAcquire` **原子**完成——谁先拿到谁执行，后到者区间相交则失败。详见 §8.7。

> **关于路权/预约的获取时机**：调度器**只判断、不占用**；**真正的 `TryAcquire`（路权）与 `TryReserve`（设备预约）
> 都在天车状态机开始执行任务时**做。拿不到就**回滚**（释放天车锁/已占用资源、任务回 `Waiting`），下一轮重新派发。
> 因此"调度判断"与"真正加锁"之间有一个窗口，由状态机的原子获取兜底。

### 8.5 CraneWorker 与状态机

**一台天车一个独立执行循环**（各自 `Task.Run`，互不阻塞），只推进自己的 `CurrentTask`，不抢别的任务。
多台天车**真正并行**：三台车各自在等自己的运动到位/握手，而不是"一台跑完、下一台才开始"。

```
Crane01Worker(Task) → 只推进 Crane01 状态机，直接 await CraneService.MoveAsync(...)
Crane02Worker(Task) → 只推进 Crane02 状态机
Crane03Worker(Task) → 只推进 Crane03 状态机
```

状态机内的运动/交互**通过 `ICraneDriver` 调用同一套方法**（绝对/相对移动、充放磁、回原点、清报警等），
与手动操作页同一套地址、同一套方法。由于移动内部会**轮询到位/超时（可能数十秒）**，
必须放在每台车自己的循环里 `await`——不能放在一个共享单循环里串行，否则一台车等点位会堵死其它车。

`ICraneDriver` 已提供自动引擎所需的全部能力（不再新增接口）：
- **命令**：`MoveAbsoluteAsync(x,y,z)` / `MoveRelativeAsync(dx,dy,dz)`（内部做基准换算）、点动、回原点、设速度、充放磁、接液盘、伺服、减速停、急停、清报警，均返回 `CraneCommandResult`；
- **阅读**：`ReadStatusAsync()` 返回 `CraneStatusDto`（显示值/绝对编码器、回原点、报警、三轴速度、X 区信号），失败返回 null；
- 引擎按 `IsSuccess`/`Code` 判断，失败抛业务异常走统一 Abort。

状态机流程（**每车一个独立循环，线性 async，逐步 `await` 到位/握手**；完整设计见《应用层设计.md》）：

```
RunFlowAsync（编排，通用唯一一份）
  AcquireResources   获取路权 + 源/目标预约（原子 TryAcquire/TryReserve；拿不到→回滚、任务回 Waiting）
  AuditSource        再审核源：PLC 点位 + 内存工件一致
  SetSpeed           设置本车三轴 速度/加速度/减速度
  PickAsync(源类型)   一大串：XY→源 → Z降 → 读 X11 有板 → 充磁(边界) → 【源特有段，含 Z 回升】
  TransitAsync        XY→目标 → 释放源设备预约 → 路权缩小到 [targetX−w/2, targetX+w/2]
  PlaceAsync(目标类型) 一大串：审核目标 → 下发参数 → 读请求上料(可选) → Z降 → 【目标特有段】→ 放磁 → Z升 → 写上料完成
  Finish             X 回安全 → 释放天车忙标志 + 路权 + 目标预约 → Complete
```

> 取料/放料按**设备类型**写死：料架 / 双头镗 / 斜床（含 Y 二次移动）/ 研磨机 / 打号机 / 下料架 各一段；中转与收尾通用。
> 运动目标换算：设备数据库 X/Y/Z **+ 本车偏移量**，Z 再减下压量（斜床/研磨 `Round(d/2)`，其余 `Round((d/2)/0.9537 + (d/2)/0.866)`，`d`=工件直径）——见《应用层设计.md》§4.1。
> 关键点：设备信号读**采集缓存**、天车状态按需实时读；`HasPieceOnCrane` 仅用于异常信息提示。

**异常处理（统一，不分充磁前后）**

状态机流程内**任何异常**（运动/握手超时、PLC·天车报警等）→ `TaskAbortCoordinator.Abort`：

1. **释放路权 + 释放源/目标设备预约**（`Release(taskId)` 幂等；源若已 `ReleaseSource` 不会重复释放）；
2. **释放天车状态**（`CurrentTask=null / State=Idle / LockedInterval=null`）；
3. **清理**：清天车与源/目标内存引用；把该工件标记为 `Discarded`（**保留记录便于追溯，不删除**）、位置置 `Discarded`；
4. **暂停线路** + 写 `statemachine.txt`/`alarm.txt` + **弹窗**（天车/设备/工件/步骤/原因）。

> **说明**：重启线路后，只要 PLC 信号正确，天车照常继续工作（丢弃任务 `Discarded`、不参与生成，不影响后续）。不再区分"充磁前/后"。
> **不是异常的情况**：`AcquireResources` 时路权/设备预约**竞争拿不到** → 走 `Rollback`（任务回 `Waiting`、不暂停），下轮重派。
> **资源生命周期（部分释放）**：到达目标后**释放源设备预约**并把路权**缩小到 `[targetX−w/2, targetX+w/2]`**；完成（回安全位后）再释放路权与目标预约。详见《应用层设计.md》§6。
> **通信闪断**不归状态机管：状态机读缓存/按需读，得不到即超时；底层重连由驱动/采集负责（§10.4）。

> **运行模式说明（现场确认）**：PLC **没有独立的"自动模式"寄存器**，`D4001` 始终写 `2`（手动），**不存在"切自动"**。
> 所谓"自动运行"只是主页面线路的**启动/停止按钮**——线路跑起来后，自动引擎**直接调用 `CraneService` 现有方法**
> （与手动操作页调用的是**同一套地址、同一套方法**）。因此自动引擎不增加任何"自动模式点位"，也不存在"切自动地址未出"的阻塞。

#### 8.5.1 多车并发的原子性

调度器**单线程**、执行器**每车一循环**。并发正确性靠三点保证：

**（1）所有权一次转移 —— 工件状态原子迁移**

`WorkpieceRuntime.TaskState`、`DeviceBase.CurrentWorkpiece`、`Crane.CurrentWorkpiece`、`Crane.Runtime.*`
目前都是**裸字段**。并发下必须保证：**一个工件任意时刻只属于一个任务/一台车；一台车一次只跑一个任务**。设计：

- **任务交接用 per-crane `Channel<TransportTask>`**（已实现，v2.41，`CraneTaskChannels`）：调度器只 `TryWrite` 入队、
  **不写 `Crane.Runtime`**；该车 Worker 出队并**独占**写本车 `Crane.Runtime`。彻底不共享写 `Crane.Runtime`，从根上消除交接竞态。
  （通道容量 1：已占位时再次派发失败，避免同车堆积。）
- 天车 `Runtime` 现由**该车 Worker 独占写**；调度器只**只读** `IsIdle`/状态用于选车。
- `TaskState` 的 `Waiting→Assigned` 用 `WorkpieceRuntime.TryTransition`（`Interlocked.CompareExchange`）**原子迁移、只成功一次**（v2.42）。

**（2）资源加锁已原子**

`RightOfWayManager`、`ResourceReservationManager`、`CandidateTaskPool`、`RuntimeTaskManager`、
`CraneRegistry`、`DeviceRegistry` 内部均有锁；`TryAcquire`/`TryReserve` 是原子的，无需额外处理。

**（3）位置单点写**

`WorkpieceRuntime.CurrentLocation` 只由天车状态机在"取放料确认"时写入（§17 不变式）。
由于该任务的源/目标设备已被预约，同一时刻不会有另一台车操作同一设备，写入按任务天然串行。

> 现状（v2.41）：`CraneWorker` 已改为**每车一个独立循环**，任务经 per-crane `Channel` 交接、Worker 独占写 Runtime；仅 `TaskState` CAS 未做，见 §19.3。

### 8.6 ResourceReservationManager

- 管理**设备资源**的预约关系
- 是设备预约状态的**唯一来源**；设备对象本身不保存 `IsReserved`
- 提供 `TryReserve(source, target)`、`Release(taskId)`、`ReleaseSource(taskId)`；**不做超时回收**
  （释放由状态机保证：拿不到预约即回滚释放、完成/异常路径释放）

### 8.7 RightOfWayManager（任务 X 区间路权）

这是本系统防止天车相撞的核心机制。**管的是空间，和设备预约是两回事。**

#### 8.7.1 路权单位

**一个正在执行的任务 = 一个 X 区间锁。**

区间由"源设备 X、目标设备 X、天车宽度"共同决定：

```
设 源设备 X = x1，目标设备 X = x2，天车宽度 = w，安全余量 = m（可选，默认 0）
x_min = min(x1, x2)
x_max = max(x1, x2)

路权区间 = [ x_min - w/2 - m ,  x_max + w/2 + m ]
```

也就是两个设备 X 坐标形成的范围，两端各外扩半个天车宽度，再各加一点安全余量。天车宽度来自数据库 `CraneConfig.Width`。

#### 8.7.2 核心规则

| 规则 | 内容 |
|---|---|
| 锁单位 | 一个任务一个区间 |
| 判断（派发时） | 调度器**只读判断** `CanAcquire`（区间是否空闲），不加锁（见 §8.4） |
| 获取（执行时） | **状态机开始执行任务时**原子 `TryAcquire`，与已锁集合求交，相交则失败；谁先拿到谁执行 |
| 失败处理 | 状态机拿不到 → **回滚**（释放天车锁、已占用资源、任务回 `Waiting`），下一轮重新派发；派发阶段判断不过则本周期不派该任务 |
| 释放时机 | **到达目标**：释放源设备预约 + 路权缩小到 `[targetX−w/2, targetX+w/2]`；**任务完成回安全位后**：释放路权 + 天车锁 + 目标设备预约 |
| 安全位 | 不参与路权；由现场设置保证不在互斥区，也不影响其它天车 |
| 死锁 | 由于空闲天车退出路权、任务结束即释放，不存在长期互等 |

#### 8.7.3 示例（重点，直接体现正确性）

假设：

```
天车1 活动范围 0 ~ 20000
天车2 活动范围 15000 ~ 30000

任务1 涉及设备 X = 5000 和 18000   → 只能分给天车1
任务2 涉及设备 X = 17000 和 25000  → 只能分给天车2
```

执行过程：

```
时刻 T：
  天车1 准备执行任务1，尝试锁 [5000 - w/2, 18000 + w/2] → 成功，加锁

时刻 T + 0.05s：
  天车2 准备执行任务2，尝试锁 [17000 - w/2, 25000 + w/2]
  → 发现 17000 落在天车1已锁区间内（区间相交）
  → TryAcquire 失败，直接 return
  → 天车2 若有其它任务就执行其它的，没有就下个周期继续判断

时刻 T + Δ：
  天车1 完成任务，X 回到安全位置
  → 释放路权区间 [5000 - w/2, 18000 + w/2]
  → 释放天车锁，任务结束

之后：
  天车2 再尝试任务2 → 加锁成功 → 执行
```

这样就从机制上保证了**两台天车不可能同时进入冲突区间**，且不需要任何动态避让算法。

> **唯一前提**：天车从安全位到源的往返路径，除任务区间本身外，不穿过其它天车的互斥区。该前提由现场安全位的设置来保证。

#### 8.7.4 为什么不用"分段交叉区配置"

早期方案考虑过把交叉区切成独立段（CrossZone），每段单独管理。讨论后放弃，原因：

- 交叉区往往很小，配置成独立段意义不大
- 天车任务本身就跨越一段连续 X 范围，用"任务区间锁"更自然
- 区间锁实现简单、正确性一眼可验证
- 安全位已经把空闲天车移出了互斥区，无需额外机制

### 8.8 AlarmManager（横切）

任何模块发现异常都可以调用 `_alarmManager.Raise(...)`。**当前实际的报警来源**（与 v1.9 一致）：

```
状态机硬故障（超时/报警 → TaskAbortCoordinator）   —— Error
采集瞬时故障（通信闪断 → 重连重试）                 —— Warning
冷启动核对（现场有料但内存无数据）                 —— Warning
        ↓
AlarmManager（内存 ActiveAlarm + Logger 落盘 alarm.txt，同源同内容合并计数）
```

> 说明：§3.4/§10.4 已把"异常只来自天车状态机"确立为主线；通信闪断按瞬时故障只记警告，不进丢弃流程。
> 旧的"预约超时/路权异常"报警来源在 P3 未实现（预约回收、路权异常检测尚无，见 §15 实现状态）。

报警页面直接读 `ActiveAlarmStore`，不需要读磁盘，保证页面刷新快。

### 8.9 TaskAbortCoordinator

任务异常终止的统一入口，详见 §10.4。

### 8.10 ITransferHandler（策略）

不同设备的取放料握手不完全一致（双头镗、斜床、研磨机各有差异），通过策略隔离，避免复制整套状态机：

```csharp
public interface ITransferHandler
{
    bool CanHandle(DeviceType type);
    Task PickAsync(Crane crane, DeviceBase source, WorkpieceTask wp, CancellationToken ct);
    Task PlaceAsync(Crane crane, DeviceBase target, WorkpieceTask wp, CancellationToken ct);
    Task WriteParamsAsync(DeviceBase device, WorkpieceInfo wp, CancellationToken ct);
}
```

实现：`LoadRackHandler` / `BoringHandler` / `LatheHandler` / `GrinderHandler` / `MarkerHandler` / `UnloadRackHandler`，
由 `TransferHandlerRegistry` 按 `DeviceType` 取。每个 handler 内部是**一整串写死的线性流程**（取料/放料各一段）；
编排器（状态机）只做 `PickAsync` / `PlaceAsync` 分派。完整流程见《应用层设计.md》§5。

**取放料确认规则**（需与 PLC 点位对齐，点位在代码类中定义）：

```
取料确认 = 到位 + 设备允许取 + 抓取动作 + 天车有料信号=1 + 设备有料信号=0
放料确认 = 到位 + 目标允许放 + 松开动作 + 目标有料信号=1 + 天车有料信号=0
```

确认成功后单点写入：

```
取料确认：Source.CurrentWorkpiece = null；Crane 持有；WorkpieceRuntime.CurrentLocation = Crane(id)
放料确认：Crane.CurrentWorkpiece = null；Target.CurrentWorkpiece = WP；CurrentLocation = Device(id)
          WorkpieceRuntime.CurrentProcess = 目标工序
```

### 9.4 日志

自动线全天（约 22h）运行，日志量大，必须**按类别分文件**并按天归档：

```
Logs/
└── 2026-09-06/
    ├── system.txt         系统：启停、配置装载、冷启动核对
    ├── communication.txt  通信：连接、重连、读写失败
    ├── collection.txt     采集：点位快照（高频，抽样落盘）
    ├── generation.txt     候选任务生成
    ├── scheduling.txt     集中调度与派发
    ├── statemachine.txt   天车状态机执行
    ├── task.txt           任务生命周期、异常丢弃
    ├── alarm.txt          报警（本质是异常日志）
    └── operation.txt      人工操作：启停、添加任务、手动操作、清障
```

规则：

- **按天分目录、按类别分文件**；单文件超限自动滚动为 `{类别}_{时间}.txt`；
  超保留天数的目录自动清理。
- **高频循环用抽样写入**：例如采集 500ms 一次，但落盘按 `Logging.SampleSeconds`（默认 20s）节流，
  避免刷爆磁盘；普通/异常事件仍即时写入。
- 异常信息落盘的同时写入内存报警（`AlarmManager`），报警页读内存即可秒级展示。

> 对应配置（appsettings）：`Logging.Directory / RetentionDays / MaxFileSizeBytes / SampleSeconds`。

## 10. 关键流程

### 10.1 正常任务流

```
用户添加工件
      ↓
RuntimeTaskManager.Add(WP001) → WorkpieceRuntime.CurrentLocation = Queue
      ↓
Collector 采集设备快照（周期 500ms）
      ↓
Generator 发现：源设备已加工完成、目标设备空闲且请求上料
      ↓
CandidateTaskPool: WP001 Boring01 → Lathe02
      ↓
Scheduler 判断路权区间/预约可用 → 选中 Crane01 → 派发（不加锁）；状态机执行时再原子取路权/预约
      ↓
Crane01Worker 推进状态机
      ↓
取料确认：Boring01.CurrentWorkpiece = null；Crane01 持有；Location = Crane(01)
      ↓
放料确认：Lathe02.CurrentWorkpiece = WP001；Location = Device(02)；CurrentProcess = Lathe
      ↓
回安全位 → 释放路权与预约
      ↓
下一周期继续生成下一道搬运任务
```

### 10.2 派发时序

```
CandidateTaskPool
      ↓
CraneScheduler（只判断，不加锁）
      ↓
CanAcquire(任务区间) / IsReserved(Source,Target)   ← 只读判断；不通过则换车/下轮重试
      ↓
Crane.CurrentTask = TransportTask
      ↓
CraneWorker 状态机启动
      ↓
（状态机开始执行时）TryAcquire 路权 + TryReserve 预约   ← 真正加锁；拿不到则回滚、任务回 Waiting
```

### 10.3 执行时序

```
CraneWorker
      ↓
CraneStateMachine
      ↓
Acquire 路权 + 预约（原子；拿不到则回滚、任务回 Waiting）
      ↓
ConfirmSource
      ↓
取料 → 引用转移 → 搬运 → 放料 → 引用转移
      ↓
更新 WorkpieceRuntime.CurrentProcess
      ↓
ReturnToSafeX（回安全位）
      ↓
释放 RightOfWay、释放 Reservation
      ↓
Crane.CurrentTask = null；State = Idle
```

### 10.4 异常处理（已确认策略）

**异常来源：只发生在状态机内部**——即天车正在执行动作（移动、取放料握手、到位等）时发生的
运动/交互/握手超时或 PLC 报警。通信闪断等不属于本流程，按瞬时故障处理：
进入重连/重试，不丢弃任务、不暂停整线。

**处理原则**

- 异常发生后由程序**自动清理，不需要操作员点击任何"清内存 / 释放锁 / 补内存"按钮**。
- 清理内容：释放路权、取消 source+target 预约、释放天车执行锁、清空天车内存状态、
  清空相关设备内存引用、把该工件标记为 `Discarded`（保留记录，不删除任务）。
- 清理完成后 `LineState = PausedByFault` 暂停整线，等人工确认现场后重新启动。
- **PLC 信号清不了**（"有板/无料"是现场现实），也不去清。

**为什么可以放心清内存**

工件身份只存内存、任务废弃即丢失（§3.5 难点 1）。清空内存后，现场即便残留实物，
也只是"有实物、无数据"：`TransportTaskGenerator` 依据内存工件数据生成任务，
因此**不会为它生成任何任务**，最坏后果仅此而已。现场人员把实物取走即可，
恢复线路后调度器重新评估，不会产生死锁、也无需人工解死锁。

**处理流程（全程 try/catch/finally，保证一定释放）**

```
天车执行动作中：运动/交互/握手超时 或 PLC 报警
        ↓
   AlarmManager 记录（内存活动报警 + alarm.txt）
        ↓
TaskAbortCoordinator.Abort(task)
   1. 停止该任务后续 PLC 动作
   2. 终止本任务流程（不再给天车单独的"故障"状态）
   3. 释放该任务持有的路权区间
   4. 取消源设备预约、目标设备预约
   5. 释放天车执行锁
   6. 清空天车内存状态（CurrentTask=null、State=Idle、LockedInterval=null）
   7. 清空相关设备/天车的内存引用（CurrentWorkpiece=null）
   8. 标记该工件为已丢弃并改位置（`TaskState=Discarded`、`CurrentLocation=Discarded`）——
      **保留任务记录便于追溯，不从 RuntimeTaskManager 删除**（与此前"移除任务"的写法不同）
   9. LineState = PausedByFault
  10. 写 task.txt + alarm.txt
  11. UI 弹出异常说明（供操作员查看）
```

**不变式（v1.9 修订）**

> 异常时程序**自动清空内存**，不依赖人工点击；允许"现场有实物、内存无数据"的状态，
> 此时该实物不参与调度，待人工取走后恢复正常。系统的正确性不依赖"内存与现场完全一致"，
> 只依赖"没有数据就不排产"，因此绝不产生需要人工解的死锁。

> 说明：状态机各步骤具体清理哪些内存字段、对应哪些 PLC 点位，待现场点位表与车间排布图确定后，
> 按状态机流程逐条细化。

恢复线路：操作员回主页面点击"启动线路"，调度器重新评估所有 PLC 正常的资源。

### 10.4.1 异常处理分层：命令结果 vs 状态机局部处理

**预期内的失败不再用异常表达**。天车命令统一返回 `CraneCommandResult`
（`IsSuccess` + `Code` + `Message`），覆盖到位、下压到位、运动超时、下压超差、通信失败、未连接、报警等。
调用方按结果码判断分支，**不靠 catch 做业务判断**：

| 结果 | 结果码 | 含义 |
|---|---|---|
| 成功 | `InPosition` / `PressureReached` / `Completed` | 到位 / 下压到位 / 通用完成 |
| 失败 | `Timeout` / `PressureOutOfRange` / `FeedbackTimeout` / `NotConnected` / `Alarm` / `Communication` / `Rejected` | 预期内失败 |

**自动引擎的处理方式**（不新增接口，直接调现有命令、按结果 `if`）：拿到 `IsSuccess=false` 时，
抛一个业务异常（如 `TransportAbortException`）以复用状态机统一的 `catch → Abort` 出口；
也可就地调 `Abort`。正常结果直接推进，不抛。

| 阶段 | 做什么 |
|---|---|
| `try` | 推进状态机步骤（调用命令、按结果 `IsSuccess`/`Code` 判断） |
| `catch` | 调 `TaskAbortCoordinator.Abort`（**统一，不分充磁前后**）：释放路权 + 源/目标预约、释放天车状态、清理当前任务、暂停线路。写 `statemachine.txt`/`alarm.txt`；**UI 弹窗说明**；**不 rethrow**（详见 §8.5、§10.4.2） |
| `finally` | 无条件复位触发位、释放该释放的东西，保证不卡在中间态 |

> **边界**：命令层只把**预期异常**（Modbus 超时/连接/IO）转成结果码；
> bug 类异常（空引用、协议解析错等）不转、继续冒泡。

**已移除全局异常兜底**：不再注册 `DispatcherUnhandledException` / `TaskScheduler.UnobservedTaskException` /
`AppDomain.UnhandledException`。预期失败由结果对象表达、业务中止由状态机本地处理；
**未预期的 bug 异常不再兜底**（按设计要求，程序将直接结束、不再统一记日志）。

### 10.4.2 统一中止（不再区分取料前后）

状态机流程内**任何异常**都执行同一套中止（`TaskAbortCoordinator.Abort`）：

| 项 | 处理 |
|---|---|
| 释放资源 | 路权 + 源/目标设备预约（`Release(taskId)` 幂等，源已释放则跳过） |
| 天车任务 | 清 `CurrentTask`、回 `Idle` |
| 工件/设备内存 | 清天车与源/目标 `CurrentWorkpiece`；工件 `TaskState=Discarded`（**保留记录**）、位置 `Discarded` |
| 线路 | **暂停**，人工处理后启动 |
| 日志/弹窗 | 写 `statemachine.txt`/`alarm.txt` + 弹窗（天车/设备/工件/步骤/原因） |
| 结果 | 重启线路后，PLC 信号正确即继续；丢弃任务 `Discarded` 不参与生成，不影响后续 |

> 之前 v2.22 的"取料前 `RollbackToSource` / 取料后 `AbortDiscard`"二分**已废止**（v2.51）。
> 竞争类（路权/预约拿不到）**不算异常**，走 `Rollback`（任务回 `Waiting`、不暂停）下轮重派。

### 10.5 冷启动核对

启动线路时执行：

```
采集全部设备/天车 PLC 状态
      ↓
内存任务为空
      ↓
若某资源显示"有料"但内存无对应任务
      ↓
   仅记录报警（提示可能有残留实物），不阻塞调度
   TransportTaskGenerator 不会为它生成任务（缺内存工件数据）
      ↓
人工把实物取走后，重新启动线路即可
```

> 冷启动同样遵循 §10.4 的不变式：**不要求人工点按钮清内存/清阻塞**，
> "有实物无数据"只是不排产，不影响系统正确性。

## 11. 状态定义

### LineState（线路状态）

```
Stopped          未启动
Starting         启动中
Running          自动运行
PauseRequested   请求暂停
Paused           已暂停
PausedByFault    故障暂停
```

### WorkpieceState（工件任务状态）

```
Waiting      等待中
Assigned     已派发
Running      执行中
Completed    已完成
Discarded    已丢弃
```

### CraneState（天车状态）

```
Idle            空闲
Reserved        已分配任务、Worker 尚未出队执行
Running         执行中
```

### ResourceState（资源可用性）

```
Available              可用
Reserved               逻辑预约中
Busy                   加工/占用中
Alarm                  报警
Disconnected           连接断开
BlockedByPhysicalState 来自 PLC 真实状态（有未知工件/伴信号等）
```

> `Reserved` 为逻辑预约；`BlockedByPhysicalState` 为物理状态，二者独立，互不替代。
>
> 注：v1.9 起异常处理不再依赖 `BlockedByPhysicalState` 与人工清障（见 §10.4）；该状态保留以备后续扩展。
>
> **v2.44**：`DeviceBase.ResourceState` 字段已删除（从不写入），枚举保留；界面按事实派生（连接/报警/预约/在制）。

## 12. 线程与周期模型

### 12.1 逻辑循环

不使用固定系统线程，采用 `Task + async/await + CancellationToken` 创建长期运行的逻辑循环，实际线程由 .NET 线程池调度。
这些循环实现为 **Generic Host 的 IHostedService**，随宿主启动/停止，**不在 UI 线程上**（UI 只做展示与事件分发）：

```
Generic Host 后台循环（线程池）
  ├─ DeviceStateCollector     **只采设备**，每 DeviceIntervalMs **并发**读全部启用设备并 WhenAll（天车不后台采集）
  ├─ TransportTaskGenerator   候选重建，每 Scheduling.GenerateIntervalMs（默认 500ms）
  ├─ CraneScheduler           集中派发，每 Scheduling.ScheduleIntervalMs（默认 500ms）；选车前**按需读**空闲天车状态
  └─ CraneWorker              推进各天车状态机，每 StateMachine.ExecuteIntervalMs（默认 500ms）

UI 线程（WPF）
  └─ RuntimeTicker            每 1s 通知各页面刷新（只读注册表/集合）

落盘：IHostedService 循环内按类别写日志；高频循环用抽样（Logging.SampleSeconds）
```

### 12.2 周期可配置

采集周期、候选生成周期、调度周期、各类超时均来自 `appsettings.json`。

### 12.3 单写者原则

每个关键状态只有一个"写者"，避免并发写导致状态错乱：

| 数据 | 唯一写者 |
|---|---|
| Device.Signals | DeviceStateCollector（天车无 Signals，按需读驱动） |
| Crane.Runtime（State / CurrentTask / LockedInterval） | 该车 CraneWorker 独占写；调度器只读 `IsIdle` 选车，**不写 Runtime**（v2.41） |
| WorkpieceRuntime.CurrentLocation | 天车状态机（取放料确认时） |
| Reservation 状态 | ResourceReservationManager |
| 路权区间 | RightOfWayManager |
| ActiveAlarm | AlarmManager |

**跨线程标量可见性**：`CraneRuntime.State/CurrentTask`、`WorkpieceRuntime.TaskState/CurrentProcess`
被"调度器 / CraneWorker / 生成器 / UI"在不同线程读写，均为 `volatile` 字段，保证"写入后其它线程立刻可见"、
不读到旧值。结构体状态（`WorkpieceRuntime.CurrentLocation`、`CraneRuntime.LockedInterval`）无法 `volatile`，
仍靠单写者原则保证一致。

## 13. 页面设计（Presentation）

所有页面只做三件事：**展示状态、接收操作、调用应用服务**。绝不直接读写 PLC、不修改状态机步骤、不抢占锁。

### 13.1 主页面

- 线路状态：自动运行 / 已暂停 / 故障暂停 / 未启动
- 启动/暂停线路（**共用一个按钮**，见《页面布局/主页面.md》§2）
- 添加任务：弹窗录入工件信息（含**斜床工艺 1~10**）→ `RuntimeTaskManager.Add(...)`
- 任务列表：工件全部字段（含**斜床工艺**）、当前工序、入线顺序、当前位置、下一道工序/位置、状态
- 行内操作：**编辑 / 启动 / 暂停 / 删除**
  - **编辑**：只允许 `Created`（添加后从未点过启动）的任务。可改 **长度 / 直径 / 左堵厚 / 右堵厚 / 堵孔 /
    打印内容 / 内孔锥度 / 圆角大小 / 斜床工艺**；**版号、序号、是否做动平衡不可改**（身份与工艺判定字段）。
    入线后一律不允许——工件可能已被取走、或已按旧参数加工过，改数据会造成"设备按旧参数加工、后续按新参数加工"的错配。
    除界面按钮置灰外，**服务端 `RuntimeTaskManager.TryUpdate` 会再判一次状态**（弹窗打开期间任务可能已被启动），
    数据用**整体替换**方式写入并**沿用 `RuntimeId`**（任务身份不变），同时写 `operation.txt` 记录改动前后。
  - 启动 / 暂停：见《页面布局/主页面.md》§4、§5
  - 删除：仅限尚未派发或已结束的任务
- 当前异常摘要

### 13.2 天车管理

- **数据来源：数据库**。列表**展示 CraneConfig 全部字段**（天车号、序号、名称、协议、IP、端口、
  StartX/EndX、宽度、安全位 X/Z、三轴偏移量 X/Y/Z、三轴速度/加速度/减速度、启用），并叠加运行态列
  （通信、XYZ、状态、当前任务、报警）。**未启用的配置也会列出**，便于再启用。
- **配置 CRUD**：新增 / 编辑 / 删除天车配置，直接读写数据库 CraneConfig；改动后重载运行态注册表。
  **线路运行中禁止修改**（保存前检查 `LineControlService.IsRunning`，运行中弹窗拒绝）；重载时排空每车任务队列（`CraneTaskChannels.Clear`）。
  **完整操作规程见 §14.3：停线改 → 关程序 → 重开 → 启动线路**（每车执行循环在启动时按天车集合建立，热重载不重建）。
- 运行态数据（XYZ、状态、任务）只来自内存与采集快照，**不落库**。
- 说明：样例/模拟**数据**已移除（不再向数据库写种子）；运行态由**真实驱动**（Modbus/FOCAS）提供，
  由 `DriverFactory` 按设备类型创建，配置读取路径不变。

### 13.3 设备管理

- **数据来源：数据库**。列表**展示 DeviceConfig 全部字段**（设备号、名称、类型、协议、IP、端口、
  物理位置 X/Y/Z、加工范围直径/长度、启用），并叠加运行态列（通信、状态、当前工件、报警）。
  **未启用的配置也会列出**。
- **配置 CRUD**：新增 / 编辑 / 删除设备配置，直接读写数据库 DeviceConfig；改动后重载运行态注册表。
  **线路运行中禁止修改**（保存前检查 `LineControlService.IsRunning`，运行中弹窗拒绝）；重载时排空每车任务队列。
  **完整操作规程见 §14.3：停线改 → 关程序 → 重开 → 启动线路。**
- 详情：基础配置 / 实时信号（按设备类型显示专属信号）/ 当前工件
- 说明同 §13.2。

### 13.4 工序展示（只读）

内置默认路线（`ProcessRoute`，共 8 节点）：

```
上料架 → 双头镗 → 斜床 → 研磨机 → 动平衡 → 打号 → 验点 → 下料
                                    └─ 无启用设备则本工序不存在 ─┘
```

页面每行显示：顺序、工序、设备类型、**工序状态**（参与工艺 / 无设备·跳过）、启用设备台数。
（v1 只读；工艺顺序以现场确认为准。）

说明：
- **工序是否参与只由一个判据决定：该设备类型有没有启用设备**
  （`ProcessRoute.AvailableDeviceFilter`，生成器 / 主页面"下一道工序" / 本页**共用同一口径**）。
  没有设备的工序（如未上线的动平衡/验点）由 `GetNextAvailable` 自动跳过，不阻塞流转。
- **有设备的工序就是必经工序**：例如数据库里配了打号机，则打号机离线或报警时工件会停在研磨机
  等它恢复，**不会跳过打号直接下料**（现场已确认：不能跳过工序）。
- **货叉**（`ForkMachine`/`ProcessType.Forking`）类与枚举已具备，但**不在默认路线上**。

### 13.5 参数设置（可分可改）

参数会随项目推进持续增多，因此**必须按类别组织，而不是一长条列表**：

- 主界面按类别展示**分类卡片**（采集 / 调度 / 天车 / 状态机 / **斜床搬运** / 日志 / …），卡片上显示类别名与参数项数。
  - **斜床搬运**：每台斜床一份 Y 二次偏移参数（顶尖距离 / 大孔偏移 / 小孔偏移），写入 `App:Transfer:Lathes`。
- **点击某个分类卡片 → 弹出该分类的参数对话框**，在弹框内编辑该类参数；确定后写回 `appsettings.json`。
- 参数项标注"立即生效"或"下次启动线路生效"。
- 新增类别只需在类别定义处扩展，界面按类别自动生成卡片与弹框，无需改页面结构。
- 除 `appsettings.json` 外，设备/天车/工艺这类结构化配置在各自页面（§13.2、§13.3）维护。

### 13.6 大屏展示（只读）

大屏的定位是**一屏看全现场信号与内存数据**，不提供任何控制按钮。

- **顶部应用服务卡片**（可选、可能多个）：展示应用服务层的实时产物，例如
  `TransportTaskGenerator` 生成的候选任务、集中调度产生的正式任务等，用于观察调度过程。
  当前阶段可为占位，随 P3 逐步填充。
- **设备卡片**（只显示**数据库启用**的设备）：
  - **卡片（紧凑）**：名称、类型、加工状态；
  - **鼠标悬浮（详情）**：连接状态、当前工件（版号/序号/长度/直径）、**全部输入信号**
    （逻辑点名，来自后台采集快照，如 `RequestLoad=1`、`HasMaterial=1`）。点位信号较多，不放在卡片上。
- **天车卡片**（只显示**数据库启用**的天车）：
  - **卡片（紧凑）**：名称、**XYZ**、状态、当前任务（source→target）、**持有路权区间**；
  - **鼠标悬浮（详情）**：连接状态、路权、当前任务与 source→target（含设备位置）、当前工件（版号/序号/长度/直径）；
  - **天车不做后台采集**（§8.2），**不显示点位信号**；连接/状态在刷新时按需读 `ICraneDriver.ReadStatusAsync`。
- **卡片边框颜色（优先级：红 > 黄 > 绿）**：

| 颜色 | 设备卡片 | 天车卡片 |
|---|---|---|
| 红 `StatusFault` | 采集失败/超时/断联（`!device.IsConnected`） | 按需读失败/报警 |
| 黄 `StatusWaiting` | 已被任务预约（`ResourceReservationManager.IsReserved`） | 有任务（`Runtime.CurrentTask != null`） |
| 绿 `StatusIdle` | 已连接且未预约 | 空闲且读正常 |

> **PLC 点位的"报警点"只是普通点位**：只在信号里展示它的 0/1，**不参与边框颜色**；边框颜色只由"连接 / 预约 / 任务"决定。

- 设备/天车可能很多，大屏**必须支持横向与纵向滚动**，保证全部卡片可见、不被截断。

### 13.7 报警处理

> **报警本质是异常日志**：异常**只来自天车状态机执行动作**时的运动/交互/握手超时与 PLC 报警
> （见 §10.4）。这些异常由 `AlarmManager` 记录，并触发自动清理（释放路权/预约/锁、清天车与设备引用、
> 把工件标记 `Discarded`，用 try/finally 保证一定释放），随后**暂停线路并弹窗**。通信闪断不属此流程，按瞬时故障重连重试，仅记警告。

- 活动报警（内存 `ActiveAlarmStore`）：时间、级别、来源、内容、系统动作、关联资源、重复次数
- 报警明细同步落盘到 `Logs/日期/alarm.txt`；同源同内容自动合并计数，避免刷屏
- 任务丢弃记录：时间、工件、异常来源、执行到哪一步、释放了哪些资源
- 历史日志查询
- **不设"人工清内存/释放锁/补内存"按钮**：异常由程序自动清理（§10.4），
  页面只做报警查看与"清除报警列表"

手动操作页（§13.8）是唯一允许人工直接写 PLC 的入口；报警页不下发任何 PLC 动作。

### 13.8 手动操作

用于人工调试与设定设备坐标：选择天车后直接向天车 PLC 下发运动与动作。
**按现场约定，手动操作不与自动线做互斥/排队**——自动线运行时人为不会手动操作，
因此不需要把手动命令发进任务队列。

- **选择天车**
- **三轴运动**
  - 绝对运动：输入目标 X/Y/Z，下发到目标坐标；  
  - 相对运动：按步长点动 `X+ / X- / Y+ / Y- / Z+ / Z-`（上位机换算成绝对目标后下发）；
  - 三轴运动参数：分别设置 **X/Y/Z 各自的速度、加速度、减速度**（共 9 项），可单独下发或随运动一起下发。
- **清除报警**
- **动作**：充磁 / 放磁 / 下压 
- **查看信号**：当前三轴坐标、报警、充磁状态、有板、下压到位等 PLC 点位信号
- 每次下发写入操作日志（`operation.txt`），便于事后追溯。

> 手动动作经 `CraneService` 写真实 PLC 数据（Modbus TCP）。
> 该页面是唯一允许"人工直接写 PLC"的入口，其余页面遵循 §13 只读/经服务的原则。

## 14. 配置与数据库设计

### 14.1 appsettings.json 分类

```
Collection   设备采集周期（DeviceIntervalMs）、通信超时
Scheduling   候选任务生成周期（GenerateIntervalMs）、调度周期（ScheduleIntervalMs）
Crane        运动超时（MoveTimeoutMs）、到位容差（PositionToleranceMm=5）、下压容差（PressureToleranceMm=15）
StateMachine 握手超时（HandshakeTimeoutMs）、状态机推进周期（ExecuteIntervalMs）
Logging      日志目录、保留天数、单文件最大容量、抽样间隔（SampleSeconds）
```

> 对应关系：`Scheduling.GenerateIntervalMs`=候选生成（TransportTaskGenerator）、`ScheduleIntervalMs`=调度（CraneScheduler）、
> `Collection.DeviceIntervalMs`=设备采集、`StateMachine.ExecuteIntervalMs`=CraneWorker 推进、
> `Crane.*`=天车运动命令（`CraneService.MoveAsync` 超时与容差）。
> 天车**不再后台采集**：运动/到位由 `CraneService` 方法实时读；调度/预检查/冷启动/大屏按需调用 `ICraneDriver.ReadStatusAsync`。
> `Collection.CraneIntervalMs` 配置已删除。
>
> **运动超时与容差改为配置提供**（v2.16）：`App:Crane:MoveTimeoutMs`（默认 60000）、
> `PositionToleranceMm`（正常 XYZ 到位，默认 5）、`PressureToleranceMm`（仅下压触发时判断是否到位，默认 15）。
> 手动页与自动引擎共用。**已移除数据库 `CraneConfig.MoveTimeoutMs`**（推翻 v2.9；字段从实体与表删除，见 `Configs/Sql/drop_unused_columns.sql`）。
>
> 注：`StateMachine.HandshakeTimeoutMs` 用于设备/天车"下发信号后读反馈"的超时（默认 60s）；`StateMachine.PickTimeoutMs`
> /`PlaceTimeoutMs` **已删除**（取料即充磁、放料即放磁，无需单独确认超时）；`Collection.CommunicationTimeoutMs` 已用于
> Modbus 客户端；`Scheduling.ReservationTimeoutMs` **已删除**（不做超时回收，释放由状态机保证）。

> 参数会持续增多，界面按"类别卡片 → 点击弹框编辑"的方式组织（§13.5）。

### 14.3 配置变更操作规程（现场约定，重要）

**结论先说**：改配置一律**在停线状态下进行，改完关闭程序、重新打开**，再启动线路。
适用于：界面改库、**直接改数据库**、改 `appsettings.json`。

**规程**

1. **停线再改**：设备/天车管理页在"线路自动运行中"会直接拒绝保存（`EnsureLineStopped()` 检查 `IsRunning`）；
   请先在主页面暂停线路，再改配置。
2. **改完关程序、重新打开**，不要指望热重载接着跑。
3. **直接改数据库也一样**：程序只在「启动」和「界面点保存」时装载配置（`ConfigurationLoader.LoadAsync`），
   直接在数据库里改表，必须重启程序才会生效。
4. 重开程序后，再到主页面「启动线路」。

**为什么必须重启 —— 热重载只重建"注册表"，不重建"运行态"**

保存配置时程序会调 `LoadAsync()`：它清空并重建设备/天车/驱动注册表与每车任务队列，
但**工件任务、设备预约、路权、以及"每台天车一个执行循环"都是启动时建立的，热重载不会重建**，
于是留下"新配置 + 旧运行对象"的混合状态：

| 热重载后残留 | 后果 |
|---|---|
| 天车执行循环仍绑定**启动那一刻**的 `Crane` 实例 | 界面/大屏**永远显示天车空闲**、看不到"忙"；执行用的是**旧的安全位、XYZ 偏移、速度**（新配置不生效） |
| 新增或重新启用的天车**没有执行循环** | 该车永远不执行任务，派给它的任务只会反复回退重试 |
| `CraneTaskChannels.Clear()` 排空未取走的任务 | 该工件已被调度器置为 `Assigned`，而生成器只处理 `Waiting` → **永久停在"已派发"**，且界面启动/暂停/删除三个按钮全灰，只能重启程序 |
| 设备注册表被清空重建、但**工件任务没清** | 已在设备上的工件因"设备上工件与任务不一致"**永远等不到候选** |
| 页面持启动时的旧快照 | 界面台数/状态与实际调度口径不一致 |

**重启为什么能全部避开**：启动时 `LoadAsync()` 把设备、天车、驱动、工件任务、候选池、天车队列、
预约、路权**全部从零建立**，不存在任何旧运行对象残留——这是把"配置变更"与"运行态"彻底解耦的最简单办法。

> 程序保留"保存即热重载"只是为了调试时能立刻看到配置生效，**不作为生产运行方式**。
> 生产一律：**停线 → 改配置 → 关程序 → 重开 → 启动线路**。

## 17. 架构不变式（开发红线）

1. 数据只有一个事实来源，谁修改谁明确
2. 候选任务随时可以重算
3. 正式任务一旦派发就属于某台天车
4. 运动状态机不参与调度
5. 设备预约与空间路权是两回事
6. 异常时程序自动清空内存并放弃该工件，不依赖人工点击；现场残留实物只是不排产，不产生死锁
7. 路权/设备预约的**真正获取必须原子**，且发生在**状态机开始执行任务时**（调度器派发时只判断、不加锁）；谁先原子拿到谁执行，失败则回滚、任务回 `Waiting`
8. 信号点位定义在代码类中，不进数据库

## 18. 附录：路权完整示例

### 18.1 场景

```
天车1 活动范围：0 ~ 20000，宽度 w
天车2 活动范围：15000 ~ 30000，宽度 w
安全位：天车1 在 0，天车2 在 30000（均不在互斥区）
```

### 18.2 两个任务

| 任务 | 设备A X | 设备B X | 路权区间 |
|---|---|---|---|
| 任务1 | 5000 | 18000 | [5000 - w/2, 18000 + w/2] |
| 任务2 | 17000 | 25000 | [17000 - w/2, 25000 + w/2] |

按天车范围，任务1 只能给天车1，任务2 只能给天车2。

### 18.3 时序

```
T0        天车1 尝试锁 [5000-w/2, 18000+w/2] → 成功
T0+0.05s  天车2 尝试锁 [17000-w/2, 25000+w/2]
          → 17000 在 [5000-w/2, 18000+w/2] 内 → 相交 → 失败 return
          天车2 不改动现场，若有其它任务则执行其它任务，否则下周期重试
T0+Δ      天车1 完成任务 → X 回安全位 0 → 释放路权与天车锁
T0+Δ+ε    天车2 重试 → 成功 → 执行任务2
```

### 18.4 结论

- 两台天车**不可能同时进入冲突区间**
- 无需动态避让算法
- 无需交叉区分段配置
- 唯一前提：安全位设置合理，往返路径不穿过他人互斥区
